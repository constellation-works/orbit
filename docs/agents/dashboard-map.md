# Dashboard map

Checked-in starting map for dashboard tasks. Read the cited files before editing or citing them; this map is not authority. No line numbers are used; symbols move.

## Where things live

- Views and entry point: `crates/orbit-web/assets/dashboard/index.html` loads `crates/orbit-web/assets/dashboard/app.js`, which imports one module per view from `crates/orbit-web/assets/dashboard/js/`. Tab and subtab wiring lives in `crates/orbit-web/assets/dashboard/js/router.js::TABS`, `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_SUBTABS` and `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_MAINS`; shared fetch and DOM helpers live in `crates/orbit-web/assets/dashboard/js/common.js::requestPanel`, `crates/orbit-web/assets/dashboard/js/common.js::fetchJson` and `crates/orbit-web/assets/dashboard/js/common.js::el`.
- API routes and handlers: `crates/orbit-web/src/api/routes.rs::router` defines every endpoint, and `crates/orbit-web/src/serve.rs::build_app` nests them under `/api` (see `crates/orbit-web/src/api/mod.rs` for the module list and `crates/orbit-web/src/api/diagnostics/mod.rs` for the diagnostics family). Health and Analytics handlers live under `crates/orbit-web/src/api/diagnostics/`, for example `crates/orbit-web/src/api/diagnostics/task_tokens.rs::diagnostics_task_tokens` and `crates/orbit-web/src/api/diagnostics/completions.rs::diagnostics_completions`.
- Task view modules: `crates/orbit-web/assets/dashboard/js/tasks.js` is the list renderer (`renderTasks`, group headers, folded notices, pinned task, public re-exports); `crates/orbit-web/assets/dashboard/js/task-lifecycle.js` owns the meta block, lifecycle and delivery-stage strips, hands chain, delivery card and OS readout; `crates/orbit-web/assets/dashboard/js/task-detail.js` owns `buildTaskDetail`, its tabs and the runs tab; `crates/orbit-web/assets/dashboard/js/task-pane.js` owns the pane render, head, resizer and keyboard navigation.
- Operations view modules: `crates/orbit-web/assets/dashboard/js/operations.js` is the facade (`initOperations`, render orchestration via `renderOperations` and `fetchAndRenderOperations`, public re-exports); `crates/orbit-web/assets/dashboard/js/operations-shared.js` owns shared state, reset registry and cell/column helpers; `crates/orbit-web/assets/dashboard/js/operations-forecast.js` owns the backlog forecast; `crates/orbit-web/assets/dashboard/js/operations-fleet.js` owns fleet rendering; `crates/orbit-web/assets/dashboard/js/operations-drain.js` owns the drain head, window and queue rows; `crates/orbit-web/assets/dashboard/js/operations-drain-controls.js` owns the start, duration and mode controls; `crates/orbit-web/assets/dashboard/js/operations-drain-capacity.js` owns capacity, throttle and provider limits including `drainHolderCounts`; `crates/orbit-web/assets/dashboard/js/operations-routines.js` owns routines and the host clock (routine rows, timeline, clock bar, failure badge, `peekRoutineFailures`); `crates/orbit-web/assets/dashboard/js/operations-auto-tasks.js` owns auto-task definitions (toggle, mint, schedule, delete, scheduler note); `crates/orbit-web/assets/dashboard/js/operations-jobs.js` owns the job catalogue and live runs (`renderJobs`, `fetchAndRenderJobs`). The Catalogue shows only jobs the server reports as manual-runnable (`manual_runnable` on `GET /api/jobs`, from `supports_no_input_submission`); delivery and other child-only or task-input jobs stay in Live and History, and the Jobs "N failing" badge counts only catalogue (manual-runnable) jobs.
- Refresh and change notices: `crates/orbit-web/assets/dashboard/js/polling.js::startDashboardPolling` runs the per-view poll and slows to its safety net while `crates/orbit-web/assets/dashboard/js/polling.js::setStreamCoverage` says the change stream covers the view. `crates/orbit-web/assets/dashboard/js/change-stream.js::onChange` delivers the notices of `GET /api/events/stream` (`crates/orbit-web/src/api/events.rs::stream_events`, which diffs store scans so another process's writes appear too); a panel that should follow changes subscribes there in `crates/orbit-web/assets/dashboard/app.js::wireChangeStream` instead of polling faster.
- Asset registration and serving: `crates/orbit-web/src/assets.rs::DASHBOARD_FILES` embeds each dashboard file, `crates/orbit-web/src/assets.rs::dashboard_file_router` serves one route per file, and `crates/orbit-web/src/lib.rs::DASHBOARD_CSS` concatenates `crates/orbit-web/assets/dashboard/css/` into the single served stylesheet. The app is assembled in `crates/orbit-web/src/serve.rs::build_app` from the asset router, `crates/orbit-web/src/serve.rs::health_router` and the API router; per-request workspace resolution is `crates/orbit-web/src/state/request.rs::Ws` over `crates/orbit-web/src/state/dashboard.rs::DashboardState`. Static vendor scripts live in `crates/orbit-web/assets/dashboard/vendor/`.

## How a view is registered and served

Route in `crates/orbit-web/src/api/routes.rs::router` selects a handler that takes `crates/orbit-web/src/state/request.rs::Ws` plus a query struct such as `crates/orbit-web/src/api/helpers.rs::DiagnosticsQuery`, runs store reads in `crates/orbit-web/src/api/helpers.rs::blocking`, maps failures with `crates/orbit-web/src/api/helpers.rs::map_runtime_error`, and returns JSON. Every API response passes `crates/orbit-web/src/api/origin.rs::require_localhost_origin` and `crates/orbit-web/src/api/origin.rs::nosniff_json_responses`, and every response from the app passes `crates/orbit-web/src/serve.rs::security_headers`; the page policy itself is `crates/orbit-web/src/assets.rs::DASHBOARD_CSP`. The matching JS module fetches that endpoint (for example `crates/orbit-web/assets/dashboard/js/metrics-tokens.js::tokensQuery` with `crates/orbit-web/assets/dashboard/js/common.js::fetchJson`) and renders into its main element. The destination appears when its tab constants in `crates/orbit-web/assets/dashboard/js/router.js::TABS`, `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_SUBTABS` or `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_MAINS` route a hash to it via `crates/orbit-web/assets/dashboard/js/router.js::setActiveTab` after `crates/orbit-web/assets/dashboard/js/router.js::initTabs`. Styling comes from the file in `crates/orbit-web/assets/dashboard/css/` that `crates/orbit-web/src/lib.rs::DASHBOARD_CSS` concatenates, in cascade order.

## Pattern a new panel or series copies

- New time series copies the shared trend ladder in `crates/orbit-web/src/api/diagnostics/trend.rs::trend_range` and `crates/orbit-web/src/api/diagnostics/trend.rs::TrendWindow` over a window built by `crates/orbit-web/src/api/diagnostics/metrics.rs::DiagnosticsRange` from `crates/orbit-web/src/api/helpers.rs::DiagnosticsQuery`; the precedent is `crates/orbit-web/src/api/diagnostics/task_tokens.rs::diagnostics_task_tokens`, with `crates/orbit-web/src/api/diagnostics/completions.rs::diagnostics_completions` as the simpler counting sibling. Its JS counterpart is `crates/orbit-web/assets/dashboard/js/metrics-tokens.js::fetchTokens` guarded by `crates/orbit-web/assets/dashboard/js/metrics-tokens.js::isCurrentTokensPayload`, drawn by `crates/orbit-web/assets/dashboard/js/metrics.js::fetchAndRenderMetrics`.
- An Analytics › Agents role panel with its own data copies `crates/orbit-web/assets/dashboard/js/agents-implementers.js::implementersPanel`: its `fetch(window)` runs beside the scorecard in `crates/orbit-web/assets/dashboard/js/agents.js::fetchAndRenderAgents` and its `hash()` joins the panel node's hash in `crates/orbit-web/assets/dashboard/js/agents.js::rolePanelNode`. Its endpoint slices the cached agent scan like `crates/orbit-web/src/api/agents.rs::agent_size_curves`, over `crates/orbit-core/src/application/agents/api.rs::agent_size_curves`.
- Turns to first edit follows that series: `crates/orbit-web/src/api/diagnostics/turns_to_edit.rs::diagnostics_turns_to_edit` and `crates/orbit-web/assets/dashboard/js/metrics-turns.js::fetchTurns`, drawn from the Turns to first edit tab in `crates/orbit-web/assets/dashboard/js/metrics.js::fetchAndRenderMetrics`.
- New view copies an existing destination end to end: route entry in `crates/orbit-web/src/api/routes.rs::router`, handler module under `crates/orbit-web/src/api/`, JS module under `crates/orbit-web/assets/dashboard/js/`, tab entry in `crates/orbit-web/assets/dashboard/js/router.js::TABS` or the matching subtab table, and a stylesheet include in `crates/orbit-web/src/lib.rs::DASHBOARD_CSS` plus an asset row in `crates/orbit-web/src/assets.rs::DASHBOARD_FILES` when it adds a file.

## Obligations a dashboard change carries

- Screenshots per the workspace guide (`CLAUDE.md` screenshot rule): attach each changed view as a task artifact under `.orbit/tmp/`, dark theme only, plus a responsive width and a before shot when practical. These task artifacts are review evidence; the PR's optional `## Screenshots` section does not gate opening.
- Goldens and guards: the served bytes and page policy are pinned by `crates/orbit-web/src/tests/dashboard_static.mjs::dashboardCsp` and `crates/orbit-web/src/tests/dashboard_static.mjs::dashboardFile` reading `crates/orbit-web/src/assets.rs::DASHBOARD_CSP` and `crates/orbit-web/src/lib.rs::DASHBOARD_CSS`; markdown rendering must go through `crates/orbit-web/assets/dashboard/js/markdown.js::renderMarkdown` or `crates/orbit-web/assets/dashboard/js/markdown.js::renderMarkdownInline` (sanitized before insertion), enforced by `crates/orbit-web/src/tests/dashboard_assets.rs::dashboard_markdown_call_sites_use_sanitizing_wrapper`, and plugin or authored HTML must never be assigned as raw innerHTML.
- Docs and lints: `missing_docs` is warn in the workspace lints (`Cargo.toml`) and `orbit-web` does not opt out, so document new public surface; update affected docs in the same PR and keep the workspace guide link in `CLAUDE.md`. How-to and validation detail lives in `docs/DEVELOPMENT.md` (dashboard fixtures, browser checks, screenshots).
