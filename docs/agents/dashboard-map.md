# Dashboard map

Checked-in starting map for dashboard tasks. Read the cited files before editing or citing them; this map is not authority. No line numbers are used; symbols move.

## Where things live

Forecast coverage must describe the same population as its totals. The With proposed scenario includes current and proposed tasks; `forecast-summary.js::proposedForecastCoverage` combines their task counters for totals and Data gaps qualifications. Shared history counters are not additive. Missing coverage stays unknown, and a missing cost percentile remains unknown in both adjusted totals and the separately labelled pre-regression baseline.

- Views and entry point: `crates/orbit-web/assets/dashboard/index.html` loads `crates/orbit-web/assets/dashboard/app.js`, which imports one module per view from `crates/orbit-web/assets/dashboard/js/`. Tab and subtab wiring lives in `crates/orbit-web/assets/dashboard/js/router.js::TABS`, `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_SUBTABS` and `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_MAINS`; shared fetch and DOM helpers live in `crates/orbit-web/assets/dashboard/js/common.js::requestPanel`, `crates/orbit-web/assets/dashboard/js/common.js::fetchJson` and `crates/orbit-web/assets/dashboard/js/common.js::el`.
- Incidents header: `incidents.js::renderIncidentWindowHeader` owns the window segments in `#diag-window`; `router.js::setDiagSubtabImpl` swaps them with the Errors count before loading. The shared header reserves the segments’ height. Incidents keeps cap information only in its list footer and retains the scan-limit warning beside the class tiles.
- API routes and handlers: `crates/orbit-web/src/api/routes.rs::router` defines every endpoint, and `crates/orbit-web/src/serve.rs::build_app` nests them under `/api` (see `crates/orbit-web/src/api/mod.rs` for the module list and `crates/orbit-web/src/api/diagnostics/mod.rs` for the diagnostics family). Health and Analytics handlers live under `crates/orbit-web/src/api/diagnostics/`, for example `crates/orbit-web/src/api/diagnostics/task_tokens.rs::diagnostics_task_tokens` and `crates/orbit-web/src/api/diagnostics/completions.rs::diagnostics_completions`.
- Global search: `crates/orbit-web/assets/dashboard/js/global-search.js::initGlobalSearch` owns the shared top-bar overlay, keyboard selection and exact task/run lookup. Title/ID substring results use `GET /api/tasks/search` (`crates/orbit-web/src/api/task_search.rs::search_dashboard_tasks`): every status, ID prefixes first, then updated time, eight compact rows with a total. Search never filters the board; `task-nav.js::applyTasksHashQuery` retires old `q` routes.
- Task view modules: `crates/orbit-web/assets/dashboard/js/tasks.js` is the list renderer (`renderTasks`, group headers, folded notices, pinned task, public re-exports); `crates/orbit-web/assets/dashboard/js/task-lifecycle.js` owns the meta block, lifecycle and delivery-stage strips, hands chain, delivery card and OS readout; `crates/orbit-web/assets/dashboard/js/task-detail.js` owns `buildTaskDetail`, its tabs and the runs tab; `crates/orbit-web/assets/dashboard/js/task-pane.js` owns the pane render, head, resizer and keyboard navigation.
- Tasks quick filter: `crates/orbit-web/assets/dashboard/js/task-quick-filter.js` owns the double-Shift bar (`wireQuickFilter`): open/close keys, drag, and `quickFilterMatches`, which `task-nav.js::filterTasks` applies on top of the chips and other board filters (`{ quick: false }` skips it, and `renderTasks` uses that for the counts and the open pane). It filters only loaded rows, client-side, and persists nothing. Task id, PR number (`github-pr` ref) and job run id match by prefix; title, branch (`job_run_branch`, one batched read per list page in `run_worktree.rs::local_run_branches`, local runs only), host and tags by substring. It is separate from global search.
- Tasks dock: `crates/orbit-web/assets/dashboard/js/log-tail.js` owns Drain, Notices, Residents and Log, including the remembered mode and keyboard switching. `router.js` normalizes retired Fleet dock links and Settings › Hosts to Observe › Fleet without changing host/workspace scope, retired Locks held links to Drain, and `#notices` to Tasks with the Notices dock tab, and `#operations/residents` to Tasks with Residents selected. - Navigation rail collapse: `crates/orbit-web/assets/dashboard/js/rail-toggle.js::initRailToggle` wires `#rail-toggle`, a sibling of the Host dialog button over its header. It remembers `orbit.dashboard.railCollapsed` independently of the Tasks dock, with no shortcut or tooltip. `rail-leaving` / `rail-entering` slide the contents before/after `rail-collapsed` changes the shell column from 200px to a 45px strip containing only the toggle (`css/shell.css`). Hidden controls become inert and focus moves to the surviving toggle. At 760px or narrower the toggle and collapse are withdrawn; widening restores the saved preference. Reduced motion skips the slide.
- Tasks dock collapse: `crates/orbit-web/assets/dashboard/js/dock-toggle.js::initDockToggle` owns Cmd+B (Ctrl+B off the Mac) and the hide/show buttons (`#dock-collapse` in the dock's tab bar, `#dock-expand` ending the filter bar), remembered in `localStorage`. `dock-collapsed` on `#tasks-main` gives the list the full width and floats the dock's message area as an open task does; the dock slides out before its grid column goes and back after it returns (`dock-leaving`, `dock-entering` in `tasks.css`). Above the one-column breakpoint only. An explicit dock target (`#tasks?dock=…`, `#notices`, Open log, Open Tasks dock) calls `dock-toggle.js::showDockBesideList` from `router.js::setActiveTabImpl`, which clears a remembered collapse at that width and leaves it unchanged on a Tasks route with no dock target or in the one-column layout.
- Failure presentation: `crates/orbit-types/src/workflow/activity_job/worktree_failure.rs` formats worktree boundary errors and reads the historical JSON-in-message format. New `step.finished` and `run.finished` events retain the redacted payload in `error_diagnostic`; the runtime, shared displayed-step projections and HTTP run-detail adapter carry it into a collapsed Diagnostic disclosure in run detail. History groups consecutive loaded failures in each workspace/job timeline by state and complete error message, with count and first/last timestamps; expanding exposes the individual run links and actions. Sorting preserves these chronological groups. Grouping is bounded to the loaded page, and filters describe that page.
- Run detail navigation: `crates/orbit-web/assets/dashboard/js/router.js::runDetailBackLabel` and `returnFromRunDetail` use page-session history entries to name and return to the view that opened the run (including another run). Direct links, reloads and new tabs fall back to Jobs › History. The existing header button in `crates/orbit-web/assets/dashboard/js/run-detail.js::renderRunDetailMeta` receives these callbacks through `app.js::runDetailContext`; `common.js::persistScopeToUrl` preserves the entry key when rewriting scope.
- Jobs › History filters: the state chip (`run_state`) and the task or job id (`task_id`, `job_id`) live in the query string, owned by `crates/orbit-web/assets/dashboard/js/runs.js` (`persistRunFilters` rewrites the entry in place). `adoptRunFiltersFromAddress` reads them back, called by `router.js` on every route to History (load, Back and Forward), so chips, search field, list and address agree; only id-shaped values are accepted.

`crates/orbit-web/assets/dashboard/js/operations-residents.js` owns the Residents dock pane (`fetchAndRenderResidents` over `GET /api/residents?all=true`: a toolbar with the resident cycle routine toggled through `POST /api/routines/toggle`; one compact row per mandate (goal, state, last activity, next wake, needs-you), those needing the operator first and ended ones behind a disclosure; and the selected mandate's detail under its row: open `resident_authority` requests answered through `POST /api/decisions/<id>/answer`, the controls its state allows through `POST /api/residents/<id>/control` and relay `POST /api/residents/<id>/relay` (a reason or direction is asked only after choosing pause, takeover, stop or relay), facts and latest checkpoint, then widen or narrow `POST /api/residents/<id>/grant` and history behind disclosures. Static vendor scripts live in `crates/orbit-web/assets/dashboard/vendor/`.

## How a view is registered and served

Route in `crates/orbit-web/src/api/routes.rs::router` selects a handler that takes `crates/orbit-web/src/state/request.rs::Ws` plus a query struct such as `crates/orbit-web/src/api/helpers.rs::DiagnosticsQuery`, runs store reads in `crates/orbit-web/src/api/helpers.rs::blocking`, maps failures with `crates/orbit-web/src/api/helpers.rs::map_runtime_error`, and returns JSON. Every API response passes `crates/orbit-web/src/api/origin.rs::require_localhost_origin` and `crates/orbit-web/src/api/origin.rs::nosniff_json_responses`, and every response from the app passes `crates/orbit-web/src/serve.rs::security_headers`; the page policy itself is `crates/orbit-web/src/assets.rs::DASHBOARD_CSP`. The matching JS module fetches that endpoint (for example `crates/orbit-web/assets/dashboard/js/metrics-tokens.js::tokensQuery` with `crates/orbit-web/assets/dashboard/js/common.js::fetchJson`) and renders into its main element. The destination appears when its tab constants in `crates/orbit-web/assets/dashboard/js/router.js::TABS`, `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_SUBTABS` or `crates/orbit-web/assets/dashboard/js/router.js::ANALYTICS_MAINS` route a hash to it via `crates/orbit-web/assets/dashboard/js/router.js::setActiveTab` after `crates/orbit-web/assets/dashboard/js/router.js::initTabs`. Styling comes from the file in `crates/orbit-web/assets/dashboard/css/` that `crates/orbit-web/src/lib.rs::DASHBOARD_CSS` concatenates, in cascade order.

Task-owned dashboard caches and presentation state use `task-shared.js::taskDispatchIdentity` (workspace and task ID), including detail/drain reads, run history, inline feedback, comment expansion and row actions. Aggregate rows also carry workspace identity through selection and pane draft reuse. Mutation responses that omit workspace fields must retain the originating task's owner before replacing a list record. The drain's shared snapshot belongs to the selected workspace; task-specific replacements carry their own owner.

The Drain card keeps its title and phase dot at the left and its native workspace-host target select at the right. The desktop dock gives that header 320–440px (`clamp(320px, 28%, 440px)` on `main.tasks-layout`); narrow cards hide the title before clipping the host. `operations-drain.js::autoDrainWindow` renders the live counts followed by the deadline. `operations-drain.js::autoDrainApprovalSummary` supplies the approval-hold line to `operations-drain-capacity.js::autoDrainCapacity`, which groups it with the capacity summary below the slot bar, preserving the tasks link and capacity help.

## Pattern a new panel or series copies

- New time series copies the shared trend ladder in `crates/orbit-web/src/api/diagnostics/trend.rs::trend_range` and `crates/orbit-web/src/api/diagnostics/trend.rs::TrendWindow` over a window built by `crates/orbit-web/src/api/diagnostics/metrics.rs::DiagnosticsRange` from `crates/orbit-web/src/api/helpers.rs::DiagnosticsQuery`; the precedent is `crates/orbit-web/src/api/diagnostics/task_tokens.rs::diagnostics_task_tokens`, with `crates/orbit-web/src/api/diagnostics/completions.rs::diagnostics_completions` as the simpler counting sibling. Its JS counterpart builds its fenced fetch with `crates/orbit-web/assets/dashboard/js/metrics-running.js::trendSource` (see `crates/orbit-web/assets/dashboard/js/metrics-tokens.js::fetchTokens` guarded by `crates/orbit-web/assets/dashboard/js/metrics-tokens.js::isCurrentTokensPayload`), drawn by `crates/orbit-web/assets/dashboard/js/metrics.js::fetchAndRenderMetrics`.
- An Analytics › Agents role panel with its own data copies `crates/orbit-web/assets/dashboard/js/agents-implementers.js::implementersPanel`: its `fetch(window)` runs beside the scorecard in `crates/orbit-web/assets/dashboard/js/agents.js::fetchAndRenderAgents` and its `hash()` joins the panel node's hash in `crates/orbit-web/assets/dashboard/js/agents.js::rolePanelNode`. Its endpoint slices the cached agent scan like `crates/orbit-web/src/api/agents.rs::agent_size_curves`, over `crates/orbit-core/src/application/agents/api.rs::agent_size_curves`.
- The Analytics › Agents Rank tab, the first tab and the default role (`AGENT_ROLES[0]` in `crates/orbit-web/assets/dashboard/js/agents.js`; `crates/orbit-web/assets/dashboard/js/router.js` sends retired `orchestrators` links there), is `crates/orbit-web/assets/dashboard/js/agents-rank.js::fetchAndRenderRank`, opened as the `rank` role from `crates/orbit-web/assets/dashboard/js/agents.js::fetchAndRenderAgents`. It reads `GET /api/agents/rank` (`crates/orbit-web/src/api/agents.rs::agent_rank`) and draws the summary strip (`summaryNode`), the refined rank table grouped by band (`ladderModel`, `ladderNode`, with a per-row breakdown), the collapsible Not ranked section (`pendingNode`) and Not scored (`notScoredNode`); the tier-switch score-against-cost chart is `crates/orbit-web/assets/dashboard/js/agents-rank-frontier.js::rankFrontierNode` (`tierCharts` decides each tier's points and frontier), and both format through `crates/orbit-web/assets/dashboard/js/agents-rank-format.js`.
- Turns to first edit follows that series: `crates/orbit-web/src/api/diagnostics/turns_to_edit.rs::diagnostics_turns_to_edit` and `crates/orbit-web/assets/dashboard/js/metrics-turns.js::fetchTurns`, drawn from the Turns to first edit tab in `crates/orbit-web/assets/dashboard/js/metrics.js::fetchAndRenderMetrics`.
- New view copies an existing destination end to end: route entry in `crates/orbit-web/src/api/routes.rs::router`, handler module under `crates/orbit-web/src/api/`, JS module under `crates/orbit-web/assets/dashboard/js/`, tab entry in `crates/orbit-web/assets/dashboard/js/router.js::TABS` or the matching subtab table, and a stylesheet include in `crates/orbit-web/src/lib.rs::DASHBOARD_CSS` plus an asset row in `crates/orbit-web/src/assets.rs::DASHBOARD_FILES` when it adds a file.
- A new view that keeps module-level payloads (cached lists, detail, proposals, or other last-visit state) retires them on workspace change. `crates/orbit-web/assets/dashboard/js/common.js::requestPanel` only resets panel DOM and fences stale request callbacks by workspace revision; it does not invalidate a module's own cached payloads. Register a `crates/orbit-web/assets/dashboard/js/common.js::onWorkspaceChange` reset that clears every cached payload and any local repaint path (media-query or breakpoint repaints, inline mobile accordions), following `crates/orbit-web/assets/dashboard/js/memory.js::retireMemoryCache`.
- Manual QA for a new view is an A→B→A workspace switch with delayed reads and local repaints: open a detail in workspace A, switch to B and back to A while reads are still in flight, then repeat at the 375px inline-accordion width to confirm no workspace-A payload paints in B and no stale payload survives the return. Per the workspace guide this is manual QA only; do not add UI tests.

## Obligations a dashboard change carries

- Screenshots per the workspace guide (`CLAUDE.md` screenshot rule): attach each changed view as a task artifact under `.orbit/tmp/`, dark theme only, plus a responsive width and a before shot when practical. These task artifacts are review evidence; the PR's optional `## Screenshots` section does not gate opening.
- Goldens and guards: the page policy `crates/orbit-web/src/assets.rs::DASHBOARD_CSP` is emitted on every dashboard route, pinned by the public HTTP test `crates/orbit-web/tests/http_api/audit_contracts.rs::dashboard_routes_emit_csp`; `crates/orbit-web/src/tests/dashboard_static.mjs` is a helper that only the workspace visual fixture (`scripts/visual-fixture-front.mjs`) and its server test (`scripts/test-visual-fixture-server.py`) load; no Rust or HTTP test uses it. Markdown rendering must go through `crates/orbit-web/assets/dashboard/js/markdown.js::renderMarkdown` or `crates/orbit-web/assets/dashboard/js/markdown.js::renderMarkdownInline` (sanitized before insertion), enforced by `crates/orbit-web/src/tests/dashboard_assets.rs::dashboard_markdown_call_sites_use_sanitizing_wrapper`, and plugin or authored HTML must never be assigned as raw innerHTML.
- Docs and lints: `missing_docs` is warn in the workspace lints (`Cargo.toml`) and `orbit-web` does not opt out, so document new public surface; update affected docs in the same PR and keep the workspace guide link in `CLAUDE.md`. How-to and validation detail lives in `docs/DEVELOPMENT.md` (dashboard fixtures, browser checks, screenshots).
