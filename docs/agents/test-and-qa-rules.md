# Test and QA rules

The full text behind the `## Tests` bullets of the root [`AGENTS.md`](../../AGENTS.md): what tests to add, how the test job is budgeted, and how a change is checked by hand.

## Tests

- Never add UI tests: no browser, Playwright or DOM-stub tests of the dashboard, web pages, docs site or desktop UI, not even for a bug fix. Check UI changes through manual QA and screenshots.
- Add tests only for an observed, reproduced defect: a focused regression check at a public CLI/API boundary that fails before the fix and passes after. No private-function tests (private fixtures driving public behavior are fine) and no speculative coverage for features, refactors or chores. This supersedes broader admission guidance in [test_strategy.md](../design-patterns/test_strategy.md), which still governs coverage priorities, retirement evidence and timing. One owner exception to this rule is recorded in the [release-QA entry](../design/fleet-notices/4_decisions.md#release-qa-exception-the-notices-fixture-may-close-its-own-notice-over-http) (ORB-25724): the `notices::operator_closes_notice_over_http_and_unprivileged_close_is_denied` case in `crates/orbit-web/tests/http_api/notices.rs` may create, close and read back its own test-owned notice over HTTP to cover the `api:/notices` and `api:/notices/{id}/close` routes, with the isolated fixture's governed operator server and no role override or live state. It admits no other new test. The existing JSONL lock-refusal fixture has a separate, narrowly scoped private-boundary exception recorded in the [task-artifacts decision](../design/task-artifacts/4_decisions.md#jsonl-append-lock-refusal-fixture).
- Every test exercises behavior a guarantee depends on. No text-matching tests (`include_str!` + `contains()` over source, assets or UI copy), except a narrow structural safety guard (CSP, sanitizer wrapper, no raw `innerHTML`) whose message names what it protects. Don't pin config or prompt policy (crew, model, schedule, complexity, wording); if a pin is warranted, cite its incident in the assertion message.
- The Check / Clippy / Test job has a hard budget of 400 seconds wall time at p90 over PR runs (queue wait reported separately). Fix slow or flaky tests at their cause; retries, hidden skips, weaker assertions or dropped checks don't count. Retire redundant cases with measured changes that name the surviving coverage, never the only guard of a security invariant, recovery path or known incident.
- Admitted unit tests live in a sibling `tests/` dir mirroring source filenames ([`test_layout.md`](../design-patterns/test_layout.md)); crate-root `tests/` is integration only. Fixtures that mutate Orbit state run in an isolated child process ([development reference](../development/qa.md#safe-mutable-cli-fixtures)).

## QA

- Do manual QA through the real CLI, MCP, API or UI, including failure paths, when it can reveal defects, and record steps, expected and actual results and evidence. Docs-only, mechanical or already covered changes may skip it with a reason. Run a candidate build (any CLI command or `web serve`) only under a disposable home with its own workspace, never the real home or the live checkout: opening state migrates it past the installed binary ([Manual QA from a managed lane](../development/qa.md#manual-qa-from-a-managed-lane)).
- A diff that changes something users see (dashboard, web pages, docs site, desktop UI) attaches screenshots of each changed view with `orbit.task.artifact` action `put`, at paths like `screenshots/<view>-<theme>-<width>.png`, captured under `.orbit/tmp/` (`$ORBIT_SCRATCH_DIR`). Cover every supported theme (the dashboard is dark-only), 375px width for responsive layouts, and a base-revision before shot when practical. Stay under the 1 MiB artifact limit (viewport captures, or JPEG/WebP). List the paths at handoff; if the host has no browser kit or the view can't render, say so. Reviewers treat unexplained missing screenshots as missing evidence. These task artifacts are review evidence; an empty optional PR `## Screenshots` section never blocks PR opening.
- Dashboard implementers start from the [dashboard map](dashboard-map.md).
- When developing, reviewing or QA-ing a UI feature (dashboard, web pages, docs site, desktop UI), go through the UI/UX rules in [STD-07](../standards/STD-07-ui-ux/STD-07.md) first, check every changed view against them, and cite a violation as `STD-07 §Rn`.
