# User Interface — Design

This document describes the current Orbit UI implementation: the local dashboard assets, the Canon Refined visual rules they rely on, and the telemetry behaviors that must stay consistent with backend data.

## 1. Dense Layout

The dashboard favors wide, dense tables and panels over narrative screens. Tight spacing, small radii, and expandable sunken detail rows preserve hierarchy without hiding root lists. Analytics › Cost (`#analytics/cost`) shows managed-execution cost and token usage for the shared window: provider-reported USD, derived estimates, the comparable same-invocation population, normalized tokens, and model attribution. A header band (title, window buttons, the managed-execution scope and the window range) sits above two tabs, Spend & tokens and Read-only exploration; the selected tab rides in the hash (`#analytics/cost?window=30d&tab=exploration`, no `tab` is Spend & tokens) and switching tabs rewrites the hash in place without a refetch. Dollar amounts show cents with thousands separators, and a non-zero amount under one cent reads `<$0.01`. It is not an agent-family ranking. The family leaderboard, narrative strip, agent cards, and insights panel were removed [ORB-15921].

Window selectors are `role="tablist"` buttons with `aria-selected`, keyboard movement, and a visible focus ring [ORB-10873].

## 2. Layered Palette

The UI uses layered dark surfaces instead of flat black: base canvas, elevated panels, sunken wells, and accent washes. Status color should stay muted and distinct; exact token values live in `./specs/theme.md` and the dashboard CSS. The page declares `color-scheme: dark` (stylesheet and meta tag) so native scrollbars, select popups, and form controls match the palette, and each view sets the document title (`<view> · orbit`) so browser tabs and history entries are distinguishable.

## 3. Typography

`Geist` carries labels, headings, and prose. `Geist Mono` is reserved for IDs, metrics, timestamps, code, and log streams so numeric and diagnostic data stays aligned. Both are self-hosted variable fonts served from `/static/fonts/`, so the dashboard makes no third-party request.

Timestamps share one clock, the formatters in `js/common.js`. A UTC | Local control at the foot of the nav rail, under the refresh line, chooses it; the choice is stored per browser under `orbit.dashboard.clock` and defaults to UTC, so a dashboard time matches the CLI. An absolute instant renders as 24-hour time with its zone abbreviation (`2026-10-07 06:31 UTC`, or `2026-10-06 23:31 PDT` when Local is selected). The rail's refresh line, the log dock and the status bar use the same 24-hour `HH:MM:SS`, with the log's date and zone in each line's title. A relative age ("5m", "in 2 h") carries its absolute instant in the title. UTC appears only where the value is defined in UTC and is always labelled: Reliability, whose window, bucket titles and axis are UTC because the server cuts them in UTC. Cron triggers are not UTC: the scheduler evaluates them in the host's local zone ([routines design](../routines/2_design.md)), so the routines and auto-tasks payloads carry that zone as `cron_zone` (IANA `name` when the host exposes one, plus `offset_seconds`) and a trigger reads `daily 07:15 PDT`, in the host zone, whose next fire beside it reads on the dashboard clock. Without a `cron_zone` a trigger makes no zone claim.

Status reads as a coloured dot and a plain word, never colour alone: status pills, filter chips, the task detail's status cell, group headings and run states all draw their dot from the element's `data-status` / `data-state` attribute. Section titles are sentence-weight headings; the small uppercase overline is kept for field labels inside a section.

## 4. Live Status

Live processing is visible through pulsing dots, spinners, buffered-log counters, periodically refreshed tiles, and compact ticker-style values. The `orbit.log` tail is viewport-bounded; overflowing rows scroll inside the log stream so its filters and follow-tail controls remain visible [T20260430-29]. When a paused buffer overflows, resuming keeps a notice of the discarded lines among the retained rows until newer rows push it out. Motion is functional: it points to active work without making the operator read raw logs first.

The tail is the Tasks dock's Log view (`#tasks?dock=log`), under its `Drain | Locks held | Log` tab bar. The URL selects the view; the agent toggle and Wrap remain local browser preferences. Its toolbar holds the level filters (All, Err, Deny, Warn), each level counting its lines among those kept, the Agent toggle for agents' stdout relays, Follow and Wrap; a caption under it gives the number of lines shown and whether the stream is live or reconnecting. Each line is its time beside a head line (a badge — `AGENT` for an agent's stdout, else the event code such as `WRN` or `INF` — then the task its fields name as `task_id=…`, linked into Tasks, then its source) over the message, which stays on one line until the line is expanded or Wrap is on. The Log tab names the worst level present (`2 warn`, `1 err`) so a problem shows while Drain is selected. The status bar at the foot of every view repeats the newest line and offers **Open log**, which opens `#tasks?dock=log`.

Tasks uses the full page width and keeps an independent, guaranteed-minimum body height. Awaiting approval and its inline Approve buttons remain on Tasks. Review approval in both the row and detail requires a selected workspace so claim admission checks the owning workspace. A completed task save takes precedence over any older in-flight detail read. When the list itself is narrower than ~620px its rows stack: the id and title share the first line (the title still on one line, cut with an ellipsis) and the crew, host and action sit below, and the search takes the full width under the title. From 1024px up the top bar is one fixed-height row on every route: the brand, provider usage, the aggregate drain label and Refresh fit beside each other, with one host warning chip when a reading is elevated or worse. Below 1024px it wraps to two rows at most (brand, drain and Refresh above provider usage), and on a phone that warning chip stays in view [ORB-14481].

The Tasks header carries one page-level **Settle merged PRs** button beside **New task**, for settling every task whose delivery PR was merged by hand at once. It is disabled in the aggregate ("All workspaces") view and on a read-only host, as the per-task recovery controls are. One confirmation explains that only tasks whose PR already merged change; it then posts to `POST /api/tasks/settle-merged` for the selected workspace (governed by the `task.settle_merged` operation, recorded with actor `dashboard`) and shows a result line — `Settled N: <task> (#<PR>), …; skipped M: <task>, …` — in the Tasks message area. The endpoint runs the owner-side settlement over every `blocked`, `in-progress` and `review` task in that workspace, reading each candidate's own recorded PRs (so a merge older than the recent-merges listing also settles), and answers `{settled, skipped}`: each settled entry gives `task_id`, `previous_status`, `status: "done"`, `pr_number`, `base_branch` and `merge_commit`, and each skipped entry gives `task_id`, `code: "settle_merged_refused"` and the `reason` that task did not settle (its PR has not merged, or it has a live run or claim). One task that cannot settle is skipped and reported; the rest still settle. The per-task **Settle merged PR** action (`POST /api/tasks/{id}/settle-merged`) remains for settling one task.

The Tasks search has a **Clear** button beside the input, including when a task-ID lookup has emptied the text. It dismisses the opened or pinned result, clears the text filter and lookup feedback, and returns focus to search without changing the selected host, workspace, time window or status chips. The cleared route drops `q` and `open`, so a reload keeps the list cleared; a delayed lookup cannot restore the dismissed detail. Direct task links and the detail's Close/collapse controls still open and close their task.

## 5. Dashboard Telemetry Consistency

Summary counts and drill-down panels must agree. The canonical denial count (`denials` in `/api/audit/summary`, the sum of `denials_sql` and `denials_v2`) is no longer shown on the Health rail [ORB-20662]; Health › Incidents › Events filtered to `status=denied` lists the denials for the chosen window [ORB-15355] [ORB-15923]. `/api/diagnostics/denials`, the per-denial evidence API, still combines v2 loop JSONL denial rows with SQLite `status = denied` audit events. SQLite filesystem boundary denials without an activity fsProfile use the stable `workspace-boundary` label [T20260428-13].

Jobs › History's Failed filter includes `failed`, `timeout` and `interrupted` outcomes in the summary, workspace and aggregate run-list APIs (`state=failed`), and client filter; successful and cancelled runs are excluded. History sends the dashboard window as `since` (omitted for `all`) plus optional `task_id` and `job_id`. The Jobs rail count is independent of that window and search: it counts pending and running job runs (in All workspaces, the sum over every available workspace, from the aggregate list's `total`) and the badge reads `N runs`, because one task is several pipeline runs. Its click opens Live. Failure rows retain their concrete state so operators can see why each run stopped and resume it. The workspace run list reconciles stale pending and running workers once per list query, including multi-state filters such as `active` and `failed`; its page and total then use the same combined state filter, with no second reconciliation for the count. Only the bounded page is hydrated for display. The aggregate run list (`/api/job-runs/all`) is observational: each workspace's page is a bounded, index-ordered read, and unlike the workspace list it never reconciles stale running runs, so polling it writes nothing. Its `total` counts every matching run across available workspaces, independent of `limit`.

Workspace and time window are one dashboard scope after [ORB-10872]. `?workspace=` and `?window=` plus the Health and Analytics hash (`#analytics/cost?window=7d`) are the source of truth. A `?workspace=` naming a workspace the server no longer serves (or one that is unavailable) is replaced by the workspace the host's fallback order picks (its remembered workspace, then an active drain, then its registry default) and the address is rewritten, so a stale bookmark opens a working dashboard instead of failing every panel. The aggregate "All workspaces" choice is written as the reserved `?workspace=all`, so a reload or shared link reopens the aggregate view rather than reading a missing parameter as "use the default workspace". Analytics › Cost fetches that window from `/api/cost?window=7d` and refuses a 24h body rather than painting it under a 7d selector. Events honor the same window as `since` and open from an actor or metric click with removable chips for actor, window, outcome/status, and source metric. The workspace chip can be removed when multiple workspaces are served, selecting the aggregate view; with a single workspace it stays as a non-interactive scope label, so Operations, Drain and distributed decisions keep their workspace selection. During a host switch it also stays non-interactive until the destination workspace list establishes cardinality; clicking the chip or activating an old chip preserves workspace state, request scope and the address bar while that list is pending. Reliability › Pipeline stays fleet-wide (ORB-10588) and labels that exception — `scope: "fleet"` plus a Fleet-wide badge and an inactive workspace-filter note — so the header workspace selector cannot imply it applies; if the dashboard window is unbounded `all`, Reliability keeps an independent labeled 7d cutoff because a rate without a range is not actionable. Like every other panel it states a cold load and a failed read in place (a failed read also turns the connection line to "panel update failed"), and a window with no settled runs says so instead of drawing a blank chart. The Runs in window summary reconciles the total as settled (succeeded plus one count per failed delivery) plus wrapper echoes rolled into that delivery plus not counted: cancelled, skipped, held, in-flight and unrecognized runs. A wrapper that failed only because a child failed (`pipeline_success_guard`, recorded as `root_cause`) is not its own failure [ORB-16400]. The failure count, the failure rate, and the by-workspace, by-job, and over-time drill-down attribute it to the leaf, and the denominator uses that same folded count. The denominator note states the rule and names all five excluded states even when none occur. When a window has no such echoes the summary still reads settled plus not counted, and those two sum to the total. Held runs remain outside the settled denominator; disclosing them does not change the failure numerator, server-provided rate or historical outcomes. Half-open cutoffs (`since ≤ t < until`) from ORB-10609 are unchanged.

**Count windows versus calendar windows.** A panel that rates each delivery picks its sample by count, so a month without deliveries leaves it as it was: Analytics › Resources (deliveries per profile, default admission's `profile_window`), Analytics › Forecast (finished tasks sampled, default 30 days with a 50-task floor) and Analytics › Agents (delivery attempts, default `last 500`, with `last 1000` available). Each names the count it used. Their count is local and never enters `?window=`. Panels that report the calendar (throughput and Metrics trends, cost per day, recent failures and Reliability rates, host health and Events) keep the shared time window. Reliability rates stay calendar-scoped: they are fleet-wide already (the broadest key), report their numerator, denominator and `low_sample`, and answer "how reliable was this period".

Run Detail > Steps now includes compact per-step agent log expanders for CLI-backed activity steps [T20260508-14]. The UI renders bounded stdout and stderr previews from `/api/runs/:id/logs`, distinguishes stderr blocks from stdout blocks, highlights structured `ERROR <target>:` lines, and keeps blob references behind the API so operators do not need to resolve content hashes manually.

Health › Incidents › Errors (`#diagnostics/incidents/errors`) combines Orbit process ERROR events with structured agent stderr. Step completion rows join the owning run's audit step to show its failure message and link to that step. The process log is host-global, so a run-affiliated row whose run belongs to another workspace is omitted from the selected workspace's view (it appears under the owning workspace); rows with no run affiliation stay. Repeated event IDs collapse into one row; distinct stderr lines from one invocation remain together in its message. Targets appear as a column, worktree prefixes are shortened with the full message available in the title, and Codex patch-verification retries (`codex_core::tools::router`) and model-manager timeouts (`codex_models_manager::manager`) live in a collapsed Agent diagnostics section. Errors requests the shared dashboard window and labels that range and the row cap; when log retention or the stderr read cap leaves the start of the window unread, the Errors header adds "covers since" with the instant its rows actually cover. Incidents defaults to unexpected failures. Each of its five class tiles counts its class's incidents, events and runs in the window and requests that class before the row limit is applied; the selected tile is visibly selected and exposes its pressed state within a named group. There is no mixed-class list, so newer refusals never push an older unexpected incident out of the limit. The header labels the newest shown incidents out of the matching total.

Analytics › Metrics (`#analytics/metrics`) is a full-width view over the shared window; its own window selector writes the same scope [ORB-15746]. The trend card has eight tabs. **implement_one duration** plots the average, p50 or p95 wall-clock time of the implement_one runs that finished in each bucket as four lines: all runs, then the low, medium and hard complexities. xhard and unset runs count toward All only and stack as `other` in the runs strip under the plot. A bucket value from fewer than three runs is drawn hollow, with an amber count in the tooltip, and a bucket without runs breaks the line. **Tasks completed** stacks the tasks that reached done in each bucket by complexity, under a total line; rejected and archived counts appear in the tooltip and the table. **Defects** stacks the bug tasks filed in each bucket under a total line, grouped by **Lineage** (fix-for-a-fix, other regression, unattributed) or **Origin** (code review, full code review, delivery review, QA sweep, full QA sweep, security review and CI failure sweep, with the rest folded into Other); a rise against the previous window reads as worse. **Tokens per task** [ORB-18364] plots the mean normalized tokens of the tasks that closed in each bucket, one line per complexity (low, medium, hard, xhard, plus unassessed when present), from `GET /api/diagnostics/task_tokens`; the trend owns its filters (Done or All closed, All invocations or Implement only, an implementing model, and up to eight compared tags) and refetches only its endpoint when they change. A compared tag splits each complexity into a solid with-tag line and a dashed without line; lines join across empty buckets, a point from fewer than three tasks is hollow, the tooltip lists n, mean and median per line and the excluded count, and the notes say that a task's time is its last index write after it closed and that tags are current ones. **Turns to first edit** [ORB-18542] plots, per complexity, the tool calls and the summed result bytes before the first file-mutating call of each task's first implement invocation (`implement_one` or `agent_implement`, whichever is earlier), from `GET /api/diagnostics/turns_to_edit`. The trend owns its filters (Done or All closed, a provider, and up to eight compared tags) and refetches only its endpoint when they change; Turns and Result bytes switch the drawn mean locally. A compared tag splits each complexity into a solid with-tag line and a dashed without line. Lines join across empty buckets. A point from fewer than three tasks is hollow. The view reports five mutually exclusive coverage categories: measured tasks; tasks whose first invocation has an empty or unavailable trace; tasks whose first invocation's trace was truncated by output capture; tasks with a populated first-invocation trace but no recognized editor; and tasks with no implement invocation. Provider options include each provider's measured count and rate; the notes show trace coverage and explain when zero measured samples reflect missing telemetry or no recognized editor calls. An empty trace does not imply that no edit occurred, and no unobserved task is averaged as zero. The tooltip lists the task count and the mean and median of both measures. **Lines changed** [ORB-18383] plots the lines added and deleted by the deliveries that landed in each bucket, from `GET /api/diagnostics/diff_stats`. **Line kind** draws code added, tests added and dashed code and tests deleted; **Crew** draws one line per implementing crew (the seven busiest, the rest folded into Other) for a chosen measure, net lines included. **Statistic** switches between totals and the per-task mean or median without a refetch, and a complexity picker refetches only this trend, so crews are compared on like work. A point from fewer than three deliveries is hollow, and the tooltip lists the delivery count, the value, the code and test totals and net lines. **Delivery friction** [ORB-18384] plots step recoveries, final recoveries, PR auto-fixes, merge conflicts, failed CI, cost and tokens per bucket from `GET /api/diagnostics/delivery_friction`, one line per family chosen in a multi-select family picker (the five event families by default). **Measure** switches between counts and rates per task done in the bucket without a refetch; the family picker and the complexity and crew pickers refetch only this trend. The filters narrow the done-task denominator and the task-scoped families (auto-fix, failed CI, cost, tokens); the recovery and conflict families come from run audit events, keep the unfiltered denominator and are tagged unfiltered. **Count views** [ORB-20003]: Tasks completed, Defects, Lines changed and **Tokens** (the total normalized tokens of closed tasks, from the same `task_tokens` payload and filters as Tokens per task, which stays as it is) carry a **Per bucket | Cumulative | Per day** toggle beside Chart | Table. Per bucket is the chart described above. Cumulative is a running total from the start of the window, so each series' last point equals its card total, with no hollow points and flat steps for empty buckets. Per day is the sum of the 24 hours ending at each bucket's close; the endpoints (`completions`, `defects`, `task_tokens`, `diff_stats`) send the buckets of history before the window (`lead_buckets`, or `lead_points` in each series; the window's `lead_buckets` counts them) so the first points cover a full day, and a host that sends none draws those points hollow and says so in the legend. The weekly buckets of an `all` window cannot tile a day, so they offer only Per bucket and Cumulative. The default is Cumulative for 1h, 24h and all and Per day for 7d and 30d; a pick is remembered per tab in the hash (`completed_view`, `defects_view`, `tokens_view`, `diff_view`) and survives a reload and a window change. Lines changed adds net code and net tests lines and a Tests ÷ code card (tests added over code added) to the running views, which sum rather than average, so they hide the statistic selector. The per-run trends (duration, tokens per task, turns to first edit, delivery friction) have no running view: a running sum of an average means nothing. A bucket with fewer than three done tasks is sparse: hollow points, an amber tooltip warning and a starred table row. Families of different units are each scaled to their own peak, with the axis in percent. The tooltip lists each family's count, tasks done and rate, plus its breakdown (recovery outcome, auto-fix blocker, failed-CI source). The Table view lists every origin, and each grouping keeps its own hidden series. The series cards are both legend and toggles: each shows the window value and its change against the previous window of the same length (`all` has none), and the last visible series cannot be hidden. Chart and Table show the same buckets, the table newest first, and a focused chart steps through buckets with the arrow keys. Buckets are clock-aligned: 5 minutes for 1h, 1 hour up to 2 days, 6 hours up to a week, 1 day up to 60 days, then weeks from Monday. Buckets narrower than 6 hours follow the dashboard clock (UTC by default, with no zone abbreviation on the axis) and wider ones stay in UTC. An empty window offers the next wider one. Below the trend sit implement_one by actor for the window (runs, average, p50, p95, change in average and a per-bucket sparkline), the slowest runs with task links, actors within one complexity over the last 30 days (bar = average, tick = p95), and outcome by complexity for all time. Those four sit in two rows of two cards, and the cards in a row share one height. The Step metrics table and the summary card beside it were retired with this view.

Health has an Incidents view after [ORB-10871]. A raw failed audit row is evidence, not an incident: one refusal repeated in a burst is one problem, and one failed run that propagates its failure up through its enclosing steps is one root cause with a chain beneath it. `/api/audit/incidents` groups the window's failed and denied audit rows by `(job run, signature)`, where the signature is `class | actor | surface | normalized message` and volatile tokens (paths, ids, numbers, timestamps, hashes) are replaced with placeholders; same-run clusters of the same class within a 60s cascade window collapse onto their earliest cluster, which becomes the incident root, with the rest recorded as its propagation chain. After [ORB-10969], a later incident whose raw message cites another incident's `job_run_id` (the parent/child `pipeline_success_guard` pattern) also folds onto that cited root, so one failed leaf is one incident with its cascade count rather than independent roots. Grouping reads only durable audit columns, so no tool, agent, workspace, or task is special-cased.

The list then rolls incidents that share a signature across runs into one row [ORB-15221]. A row is titled with the first line of its message and reads surface · actor · cadence. The cadence appears when the gaps between fires are regular (`every 20 min`); a wider spread is qualified (`about every …`). A row with no recorded message reads `<surface> failed; no message recorded` and is flagged `no message`: the grouping signature is never shown as a message. The count column gives the number of distinct runs for a recurring signature (the incident count when no run id was recorded) and the event count otherwise. Every row draws its first-to-last sighting on one axis spanning the selected window (`24h ago · 12h · now`). A lifespan narrower than 1% of the axis is a dot, and a signature seen within the last hour is drawn brighter, with its last-seen time highlighted. Rows sort by last seen, and the class is not repeated on each row. Incidents with no signature stay separate. The rollup uses the incidents the panel received; when the header says the list is the newest N of a larger match, the run count is among those N and the footer offers Load older, up to 200.

One failure is often recorded at several surfaces — a parent's wait, the worker that ran the step, a guard — each with its own signature. After [ORB-15434] every incident also carries `cause: {key, label, basis}`, derived from its root's structured evidence by shape alone, with no tool, job or workspace name special-cased. The step is the last backtick-quoted name introduced by `action`, `step` or `activity` on the message's first line (the innermost of a nested chain), else the row's `activity_id`. The code is the first `kind=`, `code=`, `error.code=` or `error_code=` value after that step on the same line, else the first `[compound_tag]` opening a message segment; a tag needs `_` or `.`, so a log level such as `[error]` is not one. Within one class, incidents share a cause when they name the same step and code (`basis: step_code`), the same step and the same normalized first line after it (`step_message`), or, with no step, the same code (`code`). Two codes under one step are two causes, since a code is its producer's statement of which failure occurred. With no step and no code the cause is the incident's own signature (`signature`), so nothing merges without evidence. The key is a stable hash of the class, basis and that evidence, so a refresh over the same events returns the same key. A signature row takes the cause of its newest incident.

The list groups by cause by default. A cause with several signatures gets a header showing the newest signature's title, the cause code, `N signatures · first … ago`, one lifespan mark per signature on the shared axis, `N sigs` and the last sighting. Its signatures are indented below it, newest first. The header is a label, not a control, and counts signatures only; runs and events stay on each signature row and are never added across them. A cause with one signature is that row alone, with the cause code beside its title. The By cause / By signature segment (buttons with `aria-pressed`) switches to the flat list, which names a structured cause after surface and actor, and the selected signature is kept. Search also matches the cause code.

Above the list, a 1h/6h/24h/7d control picks the window. 1h, 24h and 7d set the shared dashboard window; 6h exists only here and lasts until the shared window next changes. One line restates the window's incidents, failed events and runs against its audited events. Insight chips narrow the list to signatures that failed in the last hour or that record no message, and a search box matches the message, surface, actor, step, and run or task ids. Selecting a row fills the detail panel, which stays in view beside the list while the list scrolls and stacks below it when the panel is narrow. It shows class and live or quiet pills, the title, one summary sentence, and the lifespan on a wider axis. Below those are the surface, actor, step, count, first and last seen, and the cause code (`none recorded` when the cause fell back to the signature, with the grouping basis in its tooltip), then the full wrapped message with a Copy button. It lists up to five other signatures with the same cause under "Same cause, other signatures", headed by the basis that grouped them (for example "Grouped by the same step and message: action `candidate_validate`"). It then lists up to five signatures that share the normalized message but not the cause, and each run with its own incident id and run and task links. A stored message ending in an ellipsis was cut before it reached the incidents feed. The server searches all grouped audit rows for a complete matching copy before applying the five-row evidence preview. When a message ends in an ellipsis without the feed's `truncated` flag, the panel checks each incident row and its event rows for a complete matching copy: the `events` preview when present, or `sample_events` and propagation samples when `events` is absent or empty. If none has the whole text, the panel says so and links the audit events. The feed itself bounds every message it carries (see the list-message cap below); for a message it cut, the panel shows the excerpt and a Load the full message button that fetches the text from the audit row named by `message_event_id`, and Copy then copies the whole message. View run (or View runs) and Audit events link out; Audit events opens Health › Incidents › Events with the exact event ids from `event_ids` (or a complete `events` array from older servers), else with the incident's actor and surface, across every status. The panel has no repair-task action; proposals are captured from Tasks. The row keeps the actor recorded on the audit events. A clock-started routine still shows that actor, because the payload does not identify the scheduler separately.

Three counts are always rendered together with the selected window — raw failed events, grouped incidents, and affected runs. Each class tile reads `N incidents` over `M events · R runs`, and the line below the tiles restates the window's totals against the audited-event denominator. Failures stay classified as policy denials, expected refusals (an `OrbitError`-derived caller-input refusal, with the internal class label in a tooltip), or unexpected failures; classes are counted separately and never merged into one incident. Deferrals — a provider usage limit, or a run that deferred its work to a later one — have their own `deferred` class, labelled "deferred, not failed", with its own class tile [ORB-15517]. Reliability › Tools' unexpected failures by callable tool after [ORB-10969] excludes rows with no tool identity from tool denominators and rates (they are not a synthetic tool named `unknown`) and labels them as `job-run lifecycle` beside the tool cards. Nothing is dropped: the detail panel shows the grouping signature, propagation chain and a preview of up to five audit rows per incident; when `events_omitted` is positive, it shows the omitted count and offers an Open all events action that opens Events with the complete event set. Labels and denominators wrap rather than clip, and a 375px phone does not scroll horizontally.

The incidents list carries at most five newest full references in each incident's `events` array. `events_omitted` reports the exact number excluded from that preview, while `event_ids` retains every underlying raw audit row ID in the original evidence order. Incident totals, root samples and propagation links remain unchanged. The detail panel labels a bounded preview and offers an Open all events action; Events loads the complete exact-ID population in batches only after that explicit drilldown. This bounds repeated event objects in the polled list without dropping raw evidence.

List projections bound their message text after [ORB-15527]. A failed validation can record a message of a few hundred KB, and the incidents feed copied it into the incident, each of its events and samples and each propagation link, while the Errors and run-friction feeds copied it into every row on every 30-second poll. Each `message` in `/api/audit/incidents` and `/api/diagnostics/errors`, and each `stderr` in `/api/diagnostics/friction`, is now redacted in full and then cut on a character boundary to at most 2048 bytes (`LIST_MESSAGE_MAX_BYTES`), so a cut cannot leave part of a secret unredacted. The object that carries a cut field has `truncated: true` (`false` otherwise); the payload-level `truncated` on incidents still means the grouping scan limit. The full text stays reachable. `GET /api/audit/events/:id/message` returns one audit row's whole failure message, redacted the same way, and the incidents detail panel loads it on demand. Loaded messages belong to the selected host and workspace: switching either clears the detail cache, and a response from an earlier scope or visit cannot change the displayed message or its Copy value. ### Regression dimensions

Every `regression_from` link is read from the regressed task's side and given four dimensions. Each is derived from records, never guessed:

- **Nature** and **escape** come from the link's typed `regression` classification. `unclassified` is the filer's explicit non-answer; `absent` is a link stored without a classification. The two are never merged.
- **Layer** is where the fix sits: the regression task's landed paths (the landed diff the related-files query reads), else its declared footprint, else `unknown`. Each path maps through the layer table below, where the first matching row wins. The fix's layer is the one most of its paths map to, with ties going to the earlier row. Tests and docs (`ci_tests`, `docs_skills`) count only when the fix touched nothing else. `layer_source` says what was read: `landed`, `footprint` or `none`.
- **Detected by** comes from the regression task's tags through the detector table below, where the first matching row wins. Without a matching tag, a task filed by an operator (origin `operator_request`, or a filer that is not an agent, `system` or `unknown`) is `operator`, and anything else is `other`.

Both tables live in one place in code (`orbit_core::application::codebase::regression`), and their row order is the order the breakdowns list values in. Counts are over links whose regressed task was done in the window. A **breakdown** counts each value of one dimension under the filter's other dimensions, so a chip shows what choosing it would leave. The **cross-tabs** count under the whole filter. A **crew** or **complexity** rate is that slice's done tasks with a matching link ÷ its done tasks in the window, with `support` the denominator. The crew is the task's crew, else its implementer, else `unassigned`; the complexity is its tier, else `unset`. Rows below the minimum support are counted, not listed, and the rest rank by rate, then support.

`GET /api/codebase/analytics?workspace=…&window=…&min_support=…&rollup=…[&nature=…&escape=…&layer=…&detected_by=…]` answers one JSON object: the six path sections (`regressions`, `lock_contention`, `footprint_misses`, `change_coupling`, `blocked`, `rejected`, each with `rows` and `below_support`; `lock_contention` also carries the window's `reservations` and `denials` totals, and `blocked` its `causes`, `unclassified_events` and `not_failures`), `overlap` (`rows` of `path`, `rankings` and `top_rate` for each path in two or more of the four path rankings' listed rows, and `ranked_paths`, the distinct paths across those lists) and `window`, `since`, `min_support`, `rollup`, `regression_filter` (`nature`, `escape`, `layer`, `detected_by`, each a value or `null`), `touched: "declared_footprint"`, `computed_at`, `cache_ttl_seconds`, `tasks_scanned` and `row_limit`, the rows each ranking keeps. `regressions` also carries `links`, `matching_links` and `regressed` (matching regressed tasks), `breakdowns` (per dimension, every value with its `links`), `cross_tabs` (`nature_escape` and `escape_layer`, each `row`, `column`, `rows`, `columns` and `counts`), and `by_crew` and `by_complexity` (`rows` of the key, `rate`, `numerator`, `denominator` and `support`, plus `below_support`). `regressions.risk_marks` compares regression-risk marks: `enabled_at` (the first `regression_risk_marked` history event, else `null`), `before_since` and `window_days` (the first mark's window, which the before sample spans), `marked_paths`, `with_marks` and `before` (each `rate`, `numerator`, `denominator`, over distinct tasks) and `rows` of `path`, `with_marks` and `before`, most marked tasks first. With marks counts the done tasks of the selected window whose prompts marked the path; before counts the done tasks that touched it in the window before the first mark; both count a task the regression filter's links name as regressed. `regressions.attribution` is `"sites"` and `regressions.unsited` counts the matching regressed `tasks` and `links` that record no site and so count against no path. Each regressions row adds `sites` (at most 20): every distinct site under the key as `selector`, `scope` (`symbol`, `file` or `dir`), `path`, `symbol` and `kind` (`null` for a file or dir site), `tasks` and `links` (the regressed tasks and matching links naming it) and `regressed_tasks` and `regression_tasks` (their IDs), most tasks first. Each entry of a row's `regressed_tasks` adds `complexity`, `sites` (its sites under the key) and `regressions`, the links as `task_id`, `nature`, `escape`, `layer`, `layer_source`, `detected_by` and `sites`. An unknown window, rollup or filter value, or a zero minimum support, is a 400. `GET /api/codebase/show?…&path=…` takes the same selection and filter and answers `orbit codebase show`'s payload for one path from the same cached facts (the file view's Symbols list); a missing path, or one nothing in the window touched, is a 400. The server scans the tasks, the reservation history and the lock denials once per workspace runtime and keeps the facts for five minutes, single-flight; the window, minimum support, rollup and regression filter only slice those cached facts, so neither the 30-second poll nor a control change rescans. A scan rereads only the bundles of tasks whose history or comments changed since the last scan by any process: each task's history-derived facts (done and rejected times, blocks with their classified cause, widenings, left-backlog times, run marks, the landing receipt and its landed paths, and the task-pilot receipts Analytics › Agents › Pilots grades) are kept in a derived store table (`codebase_task_facts`) keyed by the task's log stamps and failed claim settlements, with a format version. Dropping that table, or a format change, only makes the next scan rebuild it with the same output. Once the five minutes pass, for up to a day, a request is answered at once from the last facts while one background scan replaces them; older than that, it waits for a scan. A ranking may therefore lag the records by more than five minutes while a refresh runs: `computed_at` says when the served scan ran, and the `Age` header how many seconds ago.

The scan and the rankings are one core service (`orbit_core::application::codebase`). The route keeps its scan in the dashboard's per-runtime cache; `orbit codebase analytics` and the read-only MCP tool `orbit.codebase.analytics` take the same window, minimum support, rollup and regression filters (`--nature`, `--escape`, `--layer`, `--detected-by`), scan once per call and return the same payload with `cache_ttl_seconds: 0`. `orbit codebase show <path>` and `orbit.codebase.show` report one rollup key (a directory or crate key with or without its trailing `/`) from the same rows: for each path ranking its rate, numerator, denominator, place in the ranking's whole order (`rank`, `null` when unranked) and `below_support`, with the tasks behind the numerator (`task_id`, `title` and the time that put it there; regressions add `crew`, `complexity`, `regression_tasks` and `regressions`, narrowed by the same filters, with `sites`, every site under the path uncapped in the analytics row's shape, and `unsited`, the declaring regressed tasks and their links that record no site; blocked adds `unclassified_tasks`). The human `orbit codebase analytics` adds the regression link counts by dimension and the crew and complexity rates under the ranking. Lock contention lists the refused requesters (a task ID, or `run:`/`invocation:` when no task was named), and change coupling lists each ranked pair holding the path with the requesters of the reservations holding both. A ranking with no row for the path is `null`, and a path nothing in the window touched is invalid input.

The file view's **Changes with** box reads related files for the file in view. Its path comes from the Hotspots table, the path search (which offers all known declared, reserved and locally available landed paths verified by task-history landing receipts, including deleted files and Markdown that takes no lock) or a shared file route. Analytics does not reconstruct missing landing receipts from delivery runs; the search and task-pilot grading use receipt-backed diffs. The selected window and minimum support apply; related measures always use files, independently of Group by. Partners sort by landed Jaccard; each partner expands to task-title links. Switching workspace invalidates in-flight responses.

`GET /api/codebase/related?workspace=…&path=…&top=10&window=30d&min_support=15`, `orbit codebase related <path>` and `orbit.codebase.related` share the core query. `top` is 1–100 (default 10); window defaults to 30d, minimum support to 15 shared landed tasks. Rows rank by landed Jaccard, then shared support, then path. Each row reports:

- `jaccard`: done tasks whose landed diff changed both files divided by tasks that changed either;
- `conditional_rate`: shared tasks divided by tasks that changed the queried file;
- `support`: `both`, `path`, `partner` and `either` task counts;
- `reservation_coupling`: reservations holding both divided by those holding either, with numerator, denominator, requesting identities and task-title evidence where those identities name workspace tasks; null when no reservation held both;
- `footprint_miss_count` and `footprint_miss_tasks`: landed tasks that declared the queried file but changed the partner without declaring it, whether or not they changed the queried file. File/symbol selectors cover that file and directory selectors cover descendants. This compares the current declared footprint (including widening) to the landed diff, independently of lock coverage. It differs from the existing footprint-misses ranking, which counts widening events;
- `tasks`: the shared landed tasks, with task IDs, titles and landed commits for evidence links.

Only done tasks with verified host delivery evidence count. The scan reads, in order: owner `landing_completed` evidence; else the latest transition into done whose note records a full 40-hex merge commit, either the owner PR completion (`; delivered by pull request #N merged as <sha>`) or an `external_merge_settled` settlement (`merged into <branch> as <sha> outside Orbit`), timed at that transition; else the typed deterministic run-delivery observation. Commit-message task IDs are never used for attribution. It then compares the local landed commit tree to its first parent (the empty tree for a root commit). Both old and new paths count for a rename; deletions count. No network fetch runs during analytics. Missing delivery records or Git objects are disclosed as `unavailable_landed_tasks`, never interpreted as a zero-change task: these are done tasks whose landing Orbit never recorded (finished by hand, or done before completion notes recorded the merge) or whose commit is not in the local checkout. Tasks tagged `no-diff-expected` without landed evidence are not counted there; with evidence they count as landed. The window uses a task-history landing timestamp when available. Without a landing receipt, only tasks whose latest done transition is inside the window are admitted to delivery observation (the task update time is used when the transition is missing); the observed landing timestamp must also be inside the window. Repository identity, the workspace's run listing and the job and activity catalogs are each read at most once per related scan, however many tasks it observes; each observation then reads only its chosen run. This view has its own bulk cap of 20 paths, reported as `large_footprint_cap`, so a release cut that bumps a dozen manifests together still counts; the coupling ranking, pilots and other sections keep the shared 12-path cap. Tasks whose diff exceeds 20 paths are excluded from all landed counts, including misses and individual support, and reported in `excluded_large`; reservations use their own timestamp and the same cap. When `rows` is empty, `empty_reason` says why (null otherwise): `no_landed_change` (no attributable landed task changed the file in the window, including an unknown path); `path_below_minimum` with `path_support` and `min_support` (the file itself changed in fewer tasks than the minimum, so no partner can reach it); `no_partner` with `path_support` (every landed task changed the file alone); or `partners_below_minimum` with `min_support`, `partners` and `max_shared`. The dashboard renders the reason in words, offers **Use all time** while the window is narrower and, for the two below-minimum cases, a rerun at the path support or the largest shared count; `orbit codebase related` names the `--min-support` value that would list a partner. The dashboard note says what the unavailable count covers. The analytics response adds receipt-backed `known_paths` for the Hotspots path search. Analytics and show perform no per-task delivery observation or Git subprocess calls. Analytics uses a five-minute history-facts cache; related queries use separate five-minute cache entries per window. Changing minimum support, rollup or the queried file reuses the appropriate facts.


## 5b. Analytics › Resources

**Resources** (`#analytics/resources`) charts this host's delivery resource profiles: what one delivery of each kind costs, minute by minute since the drain admitted it. These are the profiles admission forecasts with, the ones `orbit run profiles` lists ([auto-concurrency](../auto-concurrency/2_design.md)), so the curves explain admission decisions. The view is read-only and scoped to the selected workspace. Profiles are per host, because each host keeps its own store and capacity: the serving host answers for itself, another host's profiles come through its forward, and the aggregate view shows the usual placeholder instead of merging anything. The shared time window does not apply; each profile covers its key's last `profile_window` completed deliveries, whatever their age, across every crew model and Orbit version: the union admission falls back to when a task's crew model has too few deliveries of its own or is unknown.

A history selector, counted in deliveries, offers admission's own window (**Last `profile_window`**, the default), **Last 200** and **Last 1,000**; the latter two refetch with `?last=200|all` and never change admission's profiles. The tooltip and selection summary name an upper bound of retained completed deliveries per kind, over every crew model. `all` is a compatibility alias for the 1,000-delivery limit, not every retained delivery. An admission `profile_window` larger than 1,000 remains available through the default selection. The table's **Crew models** column counts the crew models behind each union, and how many of them have at least `min_profile_deliveries` in their own crew profile, so admission prices their tasks from it (`3 · 2 own`); its tooltip lists each crew model's deliveries in the window and its own profile's size, or that the union prices it. A work-class selector offers **Change**, **No-diff** (tasks tagged `no-diff-expected`) and each `auto-task:<template>` with a profile; Change and No-diff stay listed, disabled, until they have one. Change and No-diff overlay their complexities as series (Low, Medium and Hard in the Metrics colours, then xhard, unassessed and no complexity); a template is one series. Three plots share one x-axis of minutes since admission, from 0 to the longest horizon shown: **CPU** draws mean cores per minute with a ±1 standard deviation band, **Memory** the 90th-percentile memory (what the forecast budgets) with the mean dashed, and a short **Still running** strip the share of the window's deliveries alive at each minute, since each minute averages only the deliveries still running then. Every line ends at its horizon, where fewer than one in ten deliveries still run, with an end marker. The series cards are the legend and the toggles (the last visible one stays): each gives the peak mean CPU and its minute, the peak p90 memory, the delivery count and the horizon. A sparse profile, with fewer than `min_profile_deliveries` deliveries so that a lookup falls back to a wider profile, follows the Metrics low-sample convention: dimmed lines, a hollow end marker, an amber count and a `sparse` tag. **Cores · GiB** is the default unit; **% of host** divides by the host's cores and memory and draws `admit_cpu_percent` and `admit_memory_percent` as dashed rules, which bound the whole host's forecast rather than one delivery. It is disabled when the host's size cannot be read. Hovering, or focusing the chart and using the arrow keys (Shift for ten minutes, Home and End), moves one cursor across the three plots; the tooltip gives the minute and, per series, mean cores ± sd, p90 and mean memory, the alive share and the delivery count, or the minute that series ended. The same reading is announced through a polite live region. A table under the plots repeats each profile's deliveries, crew models, horizon, peaks, spread and build-like deliveries. A workspace with no profiles on the host says so and why.

`GET /api/resource-profiles?workspace=…` answers `workspace_id`, `built_at`, `host` (`cpu_count`, `memory_total_bytes`, or `null` when the host cannot be read), `admit_cpu_percent`, `admit_memory_percent`, `profile_window`, `last` (the `?last=` selection served, `null` for `profile_window`; anything but `all` or 1–1000 is a 400), `delivery_limit` (the effective per-key upper bound: `profile_window` by default, the numeric selection, or 1,000 for `all`), `max_last` (1,000, the maximum explicit selection and the bound for `all`), `min_profile_deliveries`, `horizon_cap_minutes` and `profiles`. Each profile is the object `orbit run profiles --json` emits for that workspace: `key` (`workspace_id`, `work_class`, `complexity`, null for a template), `delivery_count`, `crew_model` (`null`: these are the per-key unions), `crews` (per crew model, ordered by model: `crew_model`, null for deliveries that recorded none; `deliveries` in this window; `profile_deliveries`, the size of that model's own crew profile of the key, null without one), `sparse`, `horizon_minutes`, peaks, `delivery_peak_cpu` and `delivery_peak_memory_bytes` (nearest-rank p50 and p90 of each delivery's single-minute peak), spreads, `build_like`, `deliveries` (each with its `crew_model` and `orbit_version`) and the per-minute `series` (`alive`, `cpu_cores`, `cpu_stddev`, `memory_bytes`, `memory_mean_bytes`, `memory_stddev_bytes`), which runs to the window's longest delivery; the view cuts it at the horizon. They are built by the same code as admission's and kept, like admission's, until a sampled run finishes, the `[machine.auto_concurrency]` bounds or the crew-model map change, or a template's `no-diff-expected` tag is edited, so the 30-second poll does not rebuild them.

## 7. Task Write Actions

The Tasks head names the view and how many tasks show, then the search box with its icon, **Settle merged PRs** and the primary **New task** button. Below 1202px, including phone widths, the search box, **Settle merged PRs** and **New task** controls are hidden. At widths of 1202px and wider, **New task** opens a labeled modal dialog over the page (a native `<dialog>`: initial focus in Title, Tab wrapped inside it, an inert background, Escape or Cancel to dismiss and focus back on **New task**). The dialog paints in the top layer, so opening, validating, succeeding or closing it adds no height to the board and never moves the right-hand dock. Escape keeps an unsent draft, Cancel discards it, and neither cancels or resends a request already in flight: reopening shows the frozen submission's state. Following the success link, or leaving Tasks, closes it. Title, description, assessed complexity (`low`, `medium`, `hard`, `xhard`) and acceptance criteria (one per line) capture a proposed task. Title must contain non-whitespace text and at least one nonblank criterion is required. New tasks await explicit approval; creation never dispatches them. Cancel before submission writes nothing. Validation errors retain the draft. The All-workspaces view requires selecting an active target. The success link names the saved task, workspace and host. Text is assigned through DOM text/value properties.

The composer calls **`POST /api/tasks/create?workspace=<registered-id>`**, a strict action alongside the compatible existing `POST /api/tasks`. Its JSON body is `{request_id, binding, title, description, complexity, acceptance_criteria}` with optional typed `priority` (default `medium`) and `task_type` (default `chore`). Unknown fields are rejected, including status, force, system flags, actor/model, crew and authority. `request_id` is 1–128 ASCII letters, digits, dots, underscores or hyphens. Text fields are bounded to 32768 bytes, criteria to 1–100 nonblank entries and canonical payload to 256 KiB. `binding` is the opaque `creation_binding` from `GET /api/workspaces`: a content identity for the exact registered checkout, owner, role, partition and routing settings, stable across server restarts. Clients retain it with the payload; they must never refresh it automatically on an uncertain submission.

Every original request and replay passes the existing loopback Host, same-origin Origin and Fetch-Metadata guard and requires the server's explicit operator session. The server's ambient TTY, agent, override and managed-run identity grant no HTTP creation capability. Exactly one explicit, nonempty active registered workspace is required; missing, repeated, unknown and inactive selections never fall back to a default. Replica/wrong-owner writes (including a changed live machine identity), changed bindings and unreadable current registries refuse before action-key lookup. Runtime resolution pins a registry generation and checks it again before creation. Remote submissions use the existing `/api/on/<host>/tasks/create` forwarding; the addressed host applies its own origin, operator, binding and owner checks. No new persistent grants are introduced.

Original success and valid replay both return **HTTP 200** and exactly **`{id, workspace_id, request_id}`**. The existing permanent workspace-partition action-key mapping binds the request key to a canonical, default-normalized, redacted input digest and task ID, so concurrent submissions allocate one task and key reuse with changed input refuses. No receipt table or second writer is added. The screened domain service retains validation, redaction, owner coordination, allocator, events and advisories; advisories go to server tracing because the receipt is immutable. Task details, sidecars and current status are fetched through the normal read API and cannot change the creation receipt. A committed task whose later response or projection fails is recovered by replaying the same request. Receipt recovery checks the permanent key/digest mapping, the committed bundle registration in the selected workspace, and its matching envelope under the bundle lock. It does not materialize documents, events, comments or artifact payloads: damage there continues to fail ordinary detail/artifact reads without invalidating the original receipt. A reservation alone is not a committed creation; interrupted publication retries through the existing allocator and bundle recovery with the same reserved ID, while unreadable partial bundles and contradictory registrations fail closed.

Before sending, the composer saves the frozen body, binding, addressed URL, host and workspace in tab-scoped `sessionStorage`. It retains them across lost responses, server errors and reloads; retries send the same bytes and key. Fields stay disabled while the outcome is uncertain. Closing hides this submission without discarding it. A definite first input or access refusal permits correction; a refusal after uncertainty retains the key. Host/workspace switches hide the composer, retire late UI updates and cannot retarget it. Opening another scope explains where the outstanding submission belongs and prevents another proposal until it is recovered. On success, **New proposal** explicitly clears the saved receipt and starts new content with a new key. Storage failure before submission prevents the write. The saved draft contains operator-entered text and lasts for that browser tab; closing the tab removes this local recovery state, so preserve the request externally if recovery beyond the tab lifetime is needed.

The task list groups by status in the order a person has to act: **Awaiting approval** (`proposed`), review, blocked, in progress, backlog, then the closed statuses. Each group is a card: its heading names the status with its dot and count and, on the right, says what the group is waiting on. The status chips above the list are pills with the status dot and, when the loaded page is the whole match, their count; a pressed chip reads raised. The closed statuses, All and Not ready wait behind **More**, a disclosure (`aria-expanded`); a quiet chip that is on stays in view while More is closed, so the active filter is always on screen. A status with no tasks draws no card. Task rows and details read their **regression risk** from the task API's shared `riskiness` object [ORB-18690]: the observed chance that a task of its size, once done, is named by a later regression, from a size-only fit over the window's done tasks ([backlog forecast scope](../backlog-forecast/1_scope.md#per-task-riskiness-estimator)). Before a diff exists the size is the task's declared path count; once a review candidate or landed diff resolves, it is that diff's lines changed, with its own fit. An estimated row's id line ends with `risk 41%`, or `risk ~19%` when some selectors name no path, so the declared count is a lower bound; an estimate at least 1.5× the workspace base rate is amber. A row with no estimate has no risk part. For estimated rows, the tooltip and accessible label carry the breakdown: the probability with its basis and size (`Regression risk 14% · 23 declared files` or `· 412 lines changed`), the calibration evidence (`Of the 412 recent done tasks this size or larger, 61 regressed (15%)`), why a task in review or done is still sized by declared files when it is, the fit's done and regressed counts, the window and its observation cutoff (recent work has had less time to reveal regressions), the workspace's regressed and done counts with the base rate, and any selectors without a path. It names no file and no crew: the size fit attributes risk to neither. In the detail, a **Risk** chip joins the levers before the tags with the same value and tooltip; without an estimate, it says **No estimate** and its tooltip gives the reason — `no files` (no context files and no diff), `no paths` (selectors without a file or directory), `thin history` (too few done tasks in the window to fit), or `unavailable` (the estimate could not be computed). The detail pill is a keyboard-focusable button with an accessible description; hover, focus or tap reveals all the riskiness lines in a tooltip, and Escape dismisses it without closing the pane. The list, the aggregate list and the detail read one riskiness model per runtime, built from the codebase regression facts and the recorded diff sizes and cached for five minutes; a stale model is served while one background refresh replaces it, so the score never adds a per-row history scan or holds back a refresh after the first read.

The Tasks tab is writable for the actions that otherwise force a context switch to the CLI [ORB-10444] [One-Click Task Ship and Human-Attributed Dashboard Comments](./4_decisions.md#one-click-task-ship-and-human-attributed-dashboard-comments).

**Ship** appears on `backlog` tasks and is one click with no configuration UI: it posts only the task id to `POST /api/workflows/ship`. The crew is resolved by the pipeline from the task's own record and the mode from the selected workspace's registry binding, so that endpoint's omitted-`mode` default is the workspace ship mode (falling back to `pr` for a runtime with no binding). The resulting run id and state are surfaced as a notice, and a failed dispatch shows the server's error text instead of silently no-opping. Duplicate dispatch is refused: an explicit task selection whose id is already carried by a non-terminal run answers `409` with code `ship_run_in_flight` naming that run, and the UI holds a per-task guard across the double-click window. That refusal is the shared ship submission path's typed conflict, not an endpoint-local policy: the MCP tool, routine action, and interactive CLI all refuse the same duplicate ([ORB-10631], [Ship duplicate-dispatch guard lives in the shared submission path](../activity-job/4_decisions.md#ship-duplicate-dispatch-guard-lives-in-the-shared-submission-path)).

**Comments** post to `POST /api/tasks/:id/comments`, which writes through the task's existing review-thread structure rather than adding a field to the task record, so a comment survives a reload like any other task history. Authorship is forced to a human identity: an absent, agent-family, or model-constant author collapses to the `human` label, because the dashboard process may itself run inside a managed Orbit run where the runtime's ambient actor is a model.

Inline status/crew edits show a pending state on the control, refuse a duplicate submission while one is in flight, and report durable success or exact failure text next to the control (a live region, so the same feedback reaches assistive tech) rather than only logging to the console. The status control exposes every other existing status for every task, including reopening `done`, direct archival, and restoration from `archived`; the PATCH is an audited classification edit and never launches, cancels, merges, or completes work by itself. A move into `backlog` can make the task eligible for a later configured automation sweep. A successful edit offers a bounded-window undo that restores the prior value with one click, expiring automatically once the window (or a further edit) makes restoring it unsafe [ORB-10874]. Status lives in the detail pane and rows group by status, so a successful status change from the pane closes it (the `open=` URL parameter no longer names the task). Its success feedback and undo move to the row for the rest of the undo window, or to a notice in the Tasks message area when the new status is filtered out. Undoing from there leaves the pane closed. A failed, cancelled or refused change leaves the pane open with its feedback beside the control, a task outside the list and the full page stay open, and a status change that arrives through a refresh never changes which task is selected.

A linked review row shows only its pull request link in the action cell. Context selectors link to their owning task with the selected host, workspace and window. Authoritative contention keeps accessible amber (backlog) and red (in-progress) colors without adding holder, path or locking explanations; unavailable data clears stale colors and is described in each selector link's accessible label and dotted underline. Refresh preserves editors and drafts.

Description, Plan and Execution summary render their authored Markdown inside matching panels with the control surface token, a border, rounded corners and internal padding. Authored headings are smaller and quieter than the dashboard field labels; inline code, table headers and code blocks retain contrasting token-based surfaces. A long description fades inside its panel, leaving the border and padding visible, with **Show full description** / **Show less** directly below. Its inline editor stays inside the same panel and hides the toggle while editing. The panels fit both the desktop detail and the 375px phone sheet.

The task detail edits five more fields in place [ORB-12235]. **Complexity** is a `low`/`medium`/`hard`/`xhard` select with the same pending/saved/error feedback and bounded undo as the crew select; `unassessed` is deliberately not offered because the update endpoint rejects it, and a task already carrying it keeps a disabled placeholder so the select still shows what is stored. **Description**, **tags**, **acceptance criteria**, and **context files** each render their read-only view with an `edit` affordance that swaps in a text editor carrying Save and Cancel. A save sends only the field it edited — a whole-object PATCH would clobber whatever an agent wrote concurrently — and Cancel restores the view without a request. A refused save keeps the editor open with the operator's text and the server's own reason beside it; for context files that reason is the selector-existence refusal, which the editor's `allow missing context` checkbox answers for a selector naming a target the task will create. Long acceptance criteria open collapsed behind a fade with a **Show full AC** toggle that reveals the full list, mirroring the description clamp; editing the criteria continues to present every criterion. An open editor holds its detail node through the background refresh the same way a half-written comment does, so a poll never discards unsaved text.

In the aggregate ("All workspaces") view there is no ambient workspace to scope a mutation to, so every inline edit — status, crew, complexity, and the field editors — is refused unless the task carries its own `workspace_id` (present on every `/api/tasks/all` row), in which case the mutation is sent explicitly qualified to that workspace rather than the currently-selected one [ORB-10874] [ORB-12235].

## 7a. Task Comment Thread

Comments are the dashboard's long-form channel — agents post spec-length Markdown — so they render as a document rather than a log line [ORB-12645]. The thread is the detail's own **Comments** tab at the pane's full width, not a cell in the narrow side column, and each comment is a card: a 28px initial chip, the writer (an agent or crew name in the accent color with an `agent` pill beside it, a human in the foreground color), absolute and relative time, and `raw` / `copy` / `#` actions. `raw` swaps the rendered body for the Markdown it was written in, `copy` takes that source to the clipboard, and `#` scrolls to the comment and copies a link carrying its anchor. Bodies render through the same `renderMarkdown()` wrapper as every other dashboard-authored body, so sanitization is DOMPurify's and a comment carrying a `<script>` or an inline style renders inert.

A body taller than about 300px is capped behind a bottom fade, with its word count, its `##` section titles, and a **Show full comment** control; the panel header carries a `collapse all` beside the count. Height is estimated from the source rather than measured, because the detail is built off-document and a measuring pass would paint the thread a frame late. An expanded card keeps its header on screen while the body scrolls, and a body with three or more `##` sections gets an *In this comment* outline beside it, built from the rendered headings and tracking whichever section is in view. Expansion, the raw/rendered toggle, and the newest/oldest thread order are operator state rather than task data: the first two are held per comment so a background refresh that rebuilds a detail restores the thread as it was left, and the order persists in `localStorage` like the other presentation preferences.

The composer says what it accepts: the field is labeled **Add a comment**, its placeholder and hint line name the marks that carry, and a `preview` toggle renders the draft through `renderMarkdown()` before it is posted. The write itself is unchanged — still `POST /api/tasks/:id/comments` with the message alone. Counts, section lists and the outline are computed in the browser from the rendered body, so no API carries them. The history panel is untouched, including its filtering of legacy bare `commented` stubs.

Task-pilot comments with a valid 64-hex operation receipt (the comment's `operation_id` field, or an `operation_id=<64 hex>` first line on comments written before that field) and assessment JSON render labelled disposition, confidence, recommended crew and complexity, and rationale fields. Recommendations show their prior value when the receipt provides a changed value. Evidence gaps, reassessment triggers and blockers appear as lists; duplicate and already-landed findings appear when present. The raw control and copy action retain the original receipt text. Malformed or unrecognized assessments retain the normal comment rendering. `orbit task show` and its text comments projection use a one-line assessment summary, bounded to 150 characters before the timestamp and author; their JSON projections retain the full original message. These are presentation changes only; they read receipts and never change them.

## 8. Task Count, Filters, and the Tasks/Log Layout

The Tasks count uses the `/api/tasks` or `/api/tasks/all` paging envelope (`{ items, total, limit, truncated, offset, next_cursor }`) to render the current page range and matching total rather than an ambiguous `N/50`. For example, a page with twenty items at offset zero of fifty-five matches reads `1–20 of 55`; the final fifteen-item page reads `41–55 of 55`. An empty page reads `0 of N`. If a client-side filter narrows the loaded page, the count prefixes that range with the number shown, such as `3 shown · page 1–20 of 55`. The count does not name a server page limit or describe a fetched-versus-filtered relationship. The active status chips are sent to the server as an explicit `status=` filter rather than fetched wholesale and narrowed client-side, so the envelope's `total` describes the filter actually in effect [ORB-10874].

A list row is a *summary* (`"projection": "summary"`) rather than the full task [DANI-10391]. It carries the fields the collapsed row renders and filters on — id, title, status, priority, complexity, type, tags, crew and the registry-resolved `resolved_crew`/`crew_model` (a crew the registry no longer configures shows the default here, while the detail reports it as `crew_unresolved` like the CLI and tool host), timestamps, `job_run_machine`, `os_requirement` and `readiness`, attribution, dependencies, relations and context selectors — plus `comment_count`, `history_count` and `artifact_count` in place of the comment, history and artifact bodies, and no `description`, `plan`, `execution_summary` or `acceptance_criteria`. Its `status_transitions` name the governed targets without their `required_field`. The first expansion reads `GET /api/tasks/:id`, which serves the full task record `orbit task show --json` and `orbit.task.show` serve (bodies, sidecars, review gate, run-aware crew) plus the dashboard's extras (linked pull requests, each transition's evidence requirement, `job_run_navigable`, `readiness.preparing`). In a concrete-workspace Tasks view, a task-list refresh requests `detail=<id>` on `GET /api/tasks` when the selected row remains on the current page; relevant task notices on a connected stream can also trigger that refresh. The stream is unavailable in **All workspaces**, which keeps the normal 30-second full refresh, and a connected concrete-workspace Tasks view uses a three-minute full safety interval while refreshes succeed; when that stream is unavailable it uses the normal 30-second cadence. Other tabs retain their normal 30-second polling even when the workspace stream is open. A failed full refresh doubles the normal interval up to five minutes and a successful refresh resets it to 30 seconds; with the Tasks stream connected, the safety interval still keeps a three-minute floor between periodic full refreshes. In a hidden tab, the dashboard closes the stream and stops panel refreshes; it checks failed-run count and, for a selected workspace, drain phase and red-base holds once a minute. Showing the tab acknowledges the failed-run count, refreshes the dashboard and reopens the stream only when a concrete workspace is selected. The returned `detail` projection refreshes the pane without another per-task read. The All workspaces view does not carry that projection, so the pane keeps its last read painted while a fresh `GET /api/tasks/:id` is in flight. The row shows a polite loading placeholder on its first read and offers an in-place Retry when a read fails. A governed status change from a summary row reads the detail first so the evidence prompt follows the requirement the server actually holds; a forced (off-table) change needs no read. Server-side, the list page builds the crew registry once per request and issues no per-row job-run or review-ledger lookups.

Proposed and backlog rows, list and detail alike, carry `readiness: {ready, gaps, preparing}`; other statuses omit it. Each gap is `{code, severity, message, fix}` from the same orbit-types rule drain approval and backlog admission apply, so the dashboard never disagrees with the drain: `missing_context_files` blocks a proposed task and is advisory in the backlog, where its message names the missing file lock and the multi-slot wait (the same text a task write returns as a warning on the CLI, the MCP tools and the dashboard's own `POST /api/tasks`, `PATCH /api/tasks/:id` and approve, whose responses carry the core's `warnings` beside the task), `unassessed_complexity` blocks both, and a `no-diff-expected` tag clears both. These gaps cover only what an edit fixes; waits that clear on their own (dependencies, locks, host OS, crew, provider backoff, a red base) come from the drain readiness shown in the delivery card's **Readiness** row below. `preparing` is true while an active task-pilot run holds the task; the list reads those runs once per page. The row shows a chip in the `os:` badge slot: amber `not ready · N` when a gap blocks, muted `advisory · N` when every gap is advisory, a dashed `preparing` while a pilot prepares it, and nothing for a task that lacks nothing. Its tooltip lists each gap. The delivery card's **Readiness** row lists each gap after its drain headline (below), blocking gaps first: each is a grid row with the same severity chip as the row (blocking in the amber pending colour, advisory muted) in a fixed first column, and its message and `Fix:` line share the second column's left edge. A **not ready** chip after the status chips narrows the loaded page to tasks whose `ready` is false; it is client-side because readiness is derived rather than stored, and it travels in the hash as `ready=not`.

Why a backlog task is or is not starting comes from the drain readiness snapshot the Drain card reads (`GET /api/workflows/auto/readiness`), shown on the task itself. A pool-coloured square after the task id names its pool, the same four the drain admits by, **Eligible now**, **Waiting on locks** (a context lock, a group member, a reserved surface, a same-wave deferral, a live child's claim), **Waiting on capacity** (no free slot, a host throttle, a scheduled shutdown, stopped admissions) and **Waiting, other** (host OS, provider limits, dependencies, crew and the rest). and the wait follows it in words (`Waits on ORB-77`, `Throttled`, `Needs macOS host`). Its accessible name gives the pool and the wait (`Waiting on locks: waits on ORB-77`, so the visible words are not read twice) and its title names the cause without raw lock paths. Above the backlog rows one line draws the pools as a slim bar (at most 260px), a compact legend of counts and a **Why? See Tasks dock** link to `#tasks?dock=drain`; a legend entry is a pressed-state button that narrows the backlog card to that pool, and a task missing from the snapshot is counted beside the legend. Without a snapshot, or after a workspace change until the next one arrives, rows carry no dot and the card draws no strip, so a stale wait is never shown against another workspace. In a single-workspace view, the Drain poll includes `also_task=<id>` for the selected proposed or backlog task and returns its readiness in `detail_tasks`. Until that read answers, or if it fails, the Drain card's snapshot entry stands in: the detail's **Readiness** row and the backlog row's dot and pool counts keep the last snapshot entry until a later poll succeeds, and only a task with no snapshot entry shows the failed read as unknown with its error. When a successful snapshot omits the task, the detail falls back to `GET /api/workflows/auto/readiness?task=<id>` (a comma-separated list explains exactly those tasks, like `orbit run readiness <id>…`; an unknown or malformed id is a 400), which also covers tasks past the snapshot's bound of 50. Its **Readiness** row in the delivery card leads with the pool dot, pool label and one-line reason, followed by a single **Waits on** line linking every unique reported holder task and live run. Missing holders are identified as unavailable; file names never become inferred task links. Dependencies each link to their task with its status. Other waits show their readable cause and relevant server detail (for example, a red base's command and sha), without repeating raw reason codes or lock selectors. Unknown reasons remain visible as readable words and never imply eligibility. The preparation gaps follow in that row. **Ready: nothing is missing.** appears only when readiness reports the task `eligible: true` and it has no gaps; without an entry the row says the drain readiness is unknown (or still being checked) and claims no pool.

The Tasks pager has Previous and Next buttons, at the right of the status chips (on their own line when the chips fill theirs) and shown only while the list has another page. Previous follows the saved cursor history and is enabled after moving beyond the first page; Next follows `next_cursor` when the server supplies one and is disabled on the last page. Both controls are disabled while a page is loading. A polite live region in the Tasks message area reports `Loading task page…` or `Page failed: …`, and changing the status or search filters resets pagination to a new first-page request.

The active status filter and search query are represented in the `#tasks` hash (mirroring Events' own hash-encoded filters) and restated as text for assistive tech beside the count, so the current view survives a reload or the browser's back/forward button and is legible without reading each chip's color. The task a person has open is in the hash too (`open=<id>`), so a copied URL reopens it. Every task link in the dashboard (Runs, run detail, log rows, Errors, Jobs) is `#tasks?open=<id>` with the host, workspace and window in the query: it names no filter, so following it leaves the chips and search as they were, shows a task the filter hides pinned above the list, and adds a single Back step. The selected workspace is likewise mirrored into the page's `?workspace=` query parameter on every change [ORB-10874].

## 8a. Task Artifact Previews

Artifact rows in task detail stay one compact line — path, media type, size — and fetch a payload only when clicked, so a task carrying a screenshot is no more expensive to scan than any other [ORB-11365].

A supported raster artifact (`image/png`, `image/jpeg`, `image/gif`, `image/webp`) renders as an actual image rather than a download link. The preview scales to the detail column (`max-width: 100%`, `height: auto`) so it never forces the panel to scroll sideways, and it is never upscaled past its own resolution. Below 760px it takes the full column width and is capped at `60vh` so a tall screenshot cannot push the rest of the task off screen. A checkerboard background makes a transparent PNG read as transparent instead of as whatever the panel happens to sit on. Each preview carries Open (new tab) and Download controls, and the artifact path is the image's alt text — it is the only description the artifact has.

When the browser cannot decode the bytes, the preview says so and still offers the file, rather than leaving a broken-image icon.

The preview holds the fetched bytes in a `blob:` object URL, which Open and Download reuse. The dashboard's CSP therefore lists `blob:` in `img-src`, and in no other directive, so the page and the new tab Open shows (which inherits that CSP) can display it [ORB-16623]. The task-artifacts browser fixture serves the real `DASHBOARD_CSP`, so a policy that blocks the preview fails it.

The set of types rendered inline mirrors the server's `nosniff` allowlist exactly. `image/svg+xml` and `text/html` are absent from both: they are viewable formats that are also script hosts, so they stay downloads. Everything else keeps its existing text render or download link.

## 9. Operations

Operations renders routine-definition state separately from the host sweep clock [ORB-10875]. Each routine row names its source workspace, cron schedule, catalog target, last scheduler evaluation/fire, linked run outcome, and next due slot. Definition `enabled` is the versioned switch; the clock card independently reports its native provider, configured/effective cadence, loaded/active health, and native last/next tick values when available.

Routine and auto-task rows also carry an **edit** link on the cadence or trigger column. It opens a form under the row that edits only when the definition fires: a routine's trigger (cron with its missed-slot policy, a task-state trigger limited to the kinds whose job is the routine's target, or `deliveries_landed`, as the server's `trigger_options` allows) and an auto-task's schedule (cron, fixed interval or `deliveries_landed`). The form checks shape before Save and shows the server's refusal text verbatim, keeping the draft. While a form is open the 30-second refresh leaves that panel's rows alone. `POST /api/routines/trigger` and `POST /api/auto-tasks/schedule` carry the observed trigger or schedule and conflict when it changed; they run the core writes `orbit.routine.control` `set_trigger` and `orbit.auto_task.update` use, under their own `routine.set_trigger` and `auto_task.set_schedule` operator operations, and are audited like the toggles. Without that authority, the link is disabled with the reason.

Routine toggles require one concrete workspace; clock controls also require the exact local host returned by the status response, because the clock is host state while a definition is not [ORB-12236]. All-workspace mode stays readable but has no active controls. Each mutation carries its displayed target plus expected prior state, so a delayed or duplicate click conflicts instead of overwriting a newer observation. The routine write boundary rereads the definition and refuses a file retargeted since selection, and every authorized refusal is audited as a failed operation rather than a success. The UI also holds an in-flight guard, renders pending state, and reports the server's exact success or failure. Starting/stopping the native service requires confirmation; cadence is a separate control and its feedback explicitly preserves the service-state distinction. The backend accepts typed actions only and resolves routine paths and native commands itself—browser input is never interpreted as shell text. Operation success feedback across routines, the host clock, auto-tasks, jobs, and auto-drain clears automatically after about 60 seconds so confirmations do not linger as stale text once acknowledged. Pending and error messages do not time out. Start warnings and notes remain in the dock warning box above the dock tabs for the live window. A newer message or workspace change cancels an earlier pending clear so a stale timer never removes a newer message.

Jobs › Catalogue combines routine targets with recent job runs, filtered to the jobs the server reports as manual-runnable (`manual_runnable` on `GET /api/jobs`). Automation has only Routines and Auto-tasks. An operator session can use **Run** on a sweep or other no-input catalog job; `POST /api/jobs/:id/run?workspace=…` resolves the id from the catalog only, records dashboard provenance, and returns the run id and queued/submitted state. A file with the same name in the server's working directory cannot replace the catalog definition. The CLI's `orbit run job <path>` continues to accept direct YAML paths. The pane shows the receipt or server error and refreshes recent runs after submission. Pausing a routine does not disable manual Run. Delivery and other jobs that need a task id or delivery window do not appear in the Catalogue at all — they are started through Ship or Drain and their runs stay visible in Live and History; the same server decision refuses them on the manual run route. The Jobs "N failing" badge counts only the manual-runnable jobs the Catalogue shows. Read-only sessions see the authorization reason, and each job retains a copyable CLI command.

**Replay run** uses the same `job.run` operator capability and requires an explicit workspace. `POST /api/runs/:id/replay?workspace=…` accepts an optional `claim_token` body field, checks workspace and drain admission, and returns `{run_id, state}` as soon as a detached replay is persisted. Jobs › History navigates to that run for progress while every step executes again against the current catalog definition. Recorded `completion: done` input also requires the completion capability; a read-only session cannot reuse that authority by replaying a historical run.

Run detail's Events tab opens on the newest page, in chronological order, and labels the displayed range and total count. **Load earlier** pages backward; **Newest events** returns to the end. Refresh preserves the selected page's distance from the tail. Event times include seconds and the local time zone, with a date on the first row and each day change. Columns are time, kind, agent and detail; `event_type` has no column because it is the dotted spelling of the kind. The supervisor's activity samples repeat the agent's newest message every interval its output grows, so consecutive samples carrying one message fold into a single row with their time range, a count and the observed-bytes range only when they share a nonempty invocation parent, agent identity and provider. A sample with no message keeps the previous one only within that group. Samples from different invocations or without a parent identity remain separate, preserving each agent and its byte counter. Each detail is a one-line preview that opens to every field on its own line and stays open across refreshes.

The step timeline reads retry markers independently of the selected Events page, so paging does not change its markers or Retry legend. Refresh reloads that run's retries in the selected workspace; changing run or workspace clears them immediately and discards delayed responses from the old scope. The projection shows the first 100 retries in chronological order and labels omitted later markers. A 404 retry read is treated as no retry markers, like a missing optional Events or Logs stream; other failed reads, including the bounded audit scan limit, show **Retry markers unavailable** rather than implying there were no retries. The filtered read scans at most 50,000 audit rows per refresh.

Steps show a loading skeleton until the detail read settles, a read error on failure, and an empty state only for a successfully loaded run with no steps.

`GET /api/runs/:id/events?tail=true&limit=N&offset=M` opts into `{events, total, offset}`. Offset counts rows backward from the end; each returned page is chronological. The count and page are scoped to the selected workspace and `v2_envelope` source, and both come from one SQLite read snapshot so a row that commits after the count cannot change which events the page contains. Tail pages do not support `kind`; requests without `tail=true` retain the existing oldest-first array response and kind filtering.

The two-column desktop layout stacks below 900px, and routine/clock metadata collapses to one column below 600px so schedules, state labels, and controls remain scannable at 480–720px widths.

## 9a. Plugins

The Plugins tab (`#plugins`) lists what `GET /api/plugins` reports for the selected workspace — each installed or pinned plugin's version, host state, workspace toggle, diagnostic, tools, and the Orbit version its conformance goldens last passed on — so a plugin that is disabled, missing or refused at load is visible *with the step that would fix it* rather than simply absent. Certification chips mark **behind host** when that version predates the serving host's `host_orbit_version`, comparing SemVer precedence and ignoring build metadata; absent or unrecognized versions do not establish lag. Operator sessions can enable or disable at host or workspace scope; host disable asks for confirmation because it affects every workspace. Host re-enable preserves previously recorded grants and program paths and refuses changed or absent consent with a CLI remedy. Installing, removing, upgrading and editing grants stay on the CLI, where the operator answers a manifest's permission request. Sessions without operator authority see no controls.

Panels are the one place plugin-authored data is drawn, and one generic renderer draws all of them: `kv` for an object, `table` for an array of objects (columns are the union of the rows' keys), `markdown` for a string, `json` for anything else, with an ill-fitting payload falling back to `json` rather than an empty card. Markdown goes through the same sanitizing wrapper task comments use, so plugin text cannot introduce script or event handlers. Each panel is read from `GET /api/plugins/<ns>/panels/<id>`, which executes only a tool the manifest declared a panel over, with no caller-supplied input; a panel over a mutating tool cannot exist, because `orbit plugin validate` refuses that manifest by name. `links[]` render as plain tiles that open in a new tab without handing over the opener. No plugin ships markup or JavaScript, so a newly installed plugin appears here with no dashboard edit [ORB-12738].

## 9b. Leases

WORK › **Leases** (`#leases`) is the read-only view of the workspace's path leases ([path-leases design §6](../path-leases/2_design.md)) [ORB-18555]. Its first panel reads `GET /api/leases` and groups the active and queued leases by selector: who holds each path (principal, class, mode, priority and expiry) and who waits for it (a queued request or a granted lease's pending expansion), oldest queue entry first. A path under a held `dir:` selector also lists that holder with `via <selector>`, so a file inside a leased directory never reads as free. Its second panel, Recent landings, pages `GET /api/leases/notices` forward from a cursor kept per workspace visit and shows the newest 20 `overlap_landed` notices: the commit, the base branch, the delivering task, the lease and the changed paths. A long notice history catches up over several refreshes and says so meanwhile. Both reads go through Orbit Web without an operator session or a lease token; requesting, renewing and releasing stay on `orbit lease` and the lease tools. A refused read (leases disabled, or a replica checkout for notices) shows the server's message in that panel only.
