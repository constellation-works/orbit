# User Interface — Design

This document describes the current Orbit UI implementation: the local dashboard assets, the Canon Refined visual rules they rely on, and the telemetry behaviors that must stay consistent with backend data.

## 1. Dense Layout

The dashboard favors wide, dense tables and panels over narrative screens. Tight spacing, small radii, and expandable sunken detail rows preserve hierarchy without hiding root lists. The scoreboard groups per-agent metrics into Delivery, Review, Knowledge, Operations, and Attribution Cleanup sections so task attribution, review work, tool reliability, and knowledge artifacts are scanned separately. Compact pair cells stay local to the sections where they add context: `tool fail/all` is failed over total tool calls, and every abbreviated metric or leader mark has a plain-language title or accessible name [T20260428-15] [ORB-00144] [ORB-10873] [Grouped Scoreboard Sections](./4_decisions.md#grouped-scoreboard-sections).

The selected window also includes a compact Notable completions list built only from durable task fields (id, title, priority, type, optional `impact:*` tag, completion timestamp, bounded `execution_summary` excerpt). Selection is priority then completion recency, labeled as a reading order rather than a quality score. Empty Review and other snapshot-backed sections distinguish no observed events from unavailable windowed coverage: PR comments come from a lifetime snapshot with no per-event timestamps, so a finite window reports that limitation instead of "no activity". Window selectors are `role="tablist"` buttons with `aria-selected`, keyboard movement, and a visible focus ring [ORB-10873].

## 2. Layered Palette

The UI uses layered dark surfaces instead of flat black: base canvas, elevated panels, sunken wells, and accent washes. Status color should stay muted and distinct; exact token values live in `./specs/theme.md` and the dashboard CSS. The page declares `color-scheme: dark` (stylesheet and meta tag) so native scrollbars, select popups, and form controls match the palette, and each view sets the document title (`<view> · orbit`) so browser tabs and history entries are distinguishable.

## 3. Typography

`Geist` carries labels, headings, and prose. `Geist Mono` is reserved for IDs, metrics, timestamps, code, and log streams so numeric and diagnostic data stays aligned. Both are self-hosted variable fonts served from `/static/fonts/`, so the dashboard makes no third-party request.

Timestamps share one clock, the formatters in `js/common.js`. An absolute instant renders as 24-hour browser-local time with its zone abbreviation (`2026-10-06 23:31 PDT`); the top bar's refresh line, the log dock and the status bar use the same 24-hour `HH:MM:SS`, with the log's date and zone in each line's title. A relative age ("5m", "in 2 h") carries its absolute instant in the title. UTC appears only where the value is defined in UTC and is always labelled: Reliability, whose window, bucket titles and axis are UTC because the server cuts them in UTC. Cron triggers are not UTC: the scheduler evaluates them in the host's local zone ([routines design](../routines/2_design.md)), so the routines and auto-tasks payloads carry that zone as `cron_zone` (IANA `name` when the host exposes one, plus `offset_seconds`) and a trigger reads `daily 07:15 PDT`, in the host zone, whose next fire beside it reads in browser-local time with its own zone. Without a `cron_zone` a trigger makes no zone claim.

Status reads as a coloured dot and a plain word, never colour alone: status pills, filter chips, the task detail's status cell, group headings and run states all draw their dot from the element's `data-status` / `data-state` attribute. Section titles are sentence-weight headings; the small uppercase overline is kept for field labels inside a section.

## 4. Live Status

Live processing is visible through pulsing dots, spinners, buffered-log counters, periodically refreshed tiles, and compact ticker-style values. The `orbit.log` tail is viewport-bounded; overflowing rows scroll inside the log stream so its filters and follow-tail controls remain visible [T20260430-29]. Motion is functional: it points to active work without making the operator read raw logs first.

The tail is the Tasks dock's Log mode, a card under the dock's `Drain | Log` tab bar; the mode, the agent toggle and Wrap are remembered per browser via `localStorage` rather than the URL, since they are local viewing preferences rather than shared state. Its toolbar holds the level filters (All, Err, Deny, Warn), each level counting its lines among those kept, the Agent toggle for agents' stdout relays, Follow and Wrap; a caption under it gives the number of lines shown and whether the stream is live or reconnecting. Each line is its time beside a head line (a badge — `AGENT` for an agent's stdout, else the event code such as `WRN` or `INF` — then the task its fields name as `task_id=…`, linked into Tasks, then its source) over the message, which stays on one line until the line is expanded or Wrap is on. The Log tab names the worst level present (`2 warn`, `1 err`) so a problem shows while Drain is selected. The status bar at the foot of every view repeats the newest line and offers **Open log**, which opens Tasks with the dock on Log.

The task list beside the dock keeps an independent, guaranteed-minimum body height, and below ~900px the two-column Tasks layout stacks into one column instead of squeezing both into slivers. When the list itself is narrower than ~620px its rows stack: the id and title share the first line (the title still on one line, cut with an ellipsis) and the crew, host and action sit below, and the search takes the full width under the title. From 1024px up the top bar is one fixed-height row on every route: the brand, the three host readings, the aggregate drain label and Refresh fit beside each other, and the refresh line joins them from 1280px. Below 1024px it wraps to two rows at most (brand, drain and Refresh above the host readings), and on a phone all three readings stay in view in one row [ORB-14481].

## 5. Dashboard Telemetry Consistency

Summary counts and drill-down panels must agree. The canonical denial count (`denials` in `/api/audit/summary`, the sum of `denials_sql` and `denials_v2`) is the denial badge beside Audit in the rail, and clicking it opens Audit › Events filtered to `status=denied` for the window it counted [ORB-15355]. `/api/diagnostics/denials`, the per-denial evidence API, still combines v2 loop JSONL denial rows with SQLite `status = denied` audit events. SQLite filesystem boundary denials without an activity fsProfile use the stable `workspace-boundary` label [T20260428-13].

The failed-runs count beside Runs in the rail and Recent Runs' Failed filter count the same outcomes: the summary, workspace and aggregate run-list APIs (`state=failed`), and client filter all include `failed`, `timeout`, and `interrupted` outcomes; successful and cancelled runs are excluded. The Runs list sends the dashboard window as `since` (omitted for `all`) plus optional `task_id` and `job_id`. Clicking the rail count opens that list on Failed for the window the count was computed in, with any task or job search cleared, so the list total matches the badge. When the dashboard window is `all`, the badge is still the summary's 24h count and the click adopts that window. Failure rows retain their concrete state so operators can see why each run stopped and resume it. The aggregate run list (`/api/job-runs/all`) is observational: each workspace's page is a bounded, index-ordered read, and unlike the workspace list it never reconciles stale running runs, so polling it writes nothing.

Workspace and time window are one dashboard scope after [ORB-10872]. `?workspace=` and `?window=` plus the diagnostics hash (`#diagnostics/scoreboard?window=7d`) are the source of truth. A `?workspace=` naming a workspace the server no longer serves (or one that is unavailable) is replaced by the server's default workspace and the address is rewritten, so a stale bookmark opens a working dashboard instead of failing every panel. The aggregate "All workspaces" choice is written as the reserved `?workspace=all`, so a reload or shared link reopens the aggregate view rather than reading a missing parameter as "use the default workspace". Scoreboard delivery/operations and the Managed Execution cost/token panel share that window: a 7d selection fetches one `/api/scoreboard?window=7d` payload, and a 24h body is refused rather than painted under a 7d selector. Audit Events honor the same window as `since` and open from an actor or metric click with removable chips for actor, window, outcome/status, and source metric. The workspace chip can be removed when multiple workspaces are served, selecting the aggregate view; with a single workspace it stays as a non-interactive scope label, so Operations, Drain and distributed decisions keep their workspace selection. Reliability stays fleet-wide (ORB-10588) and labels that exception — `scope: "fleet"` plus a Fleet-wide badge and an inactive workspace-filter note — so the header workspace selector cannot imply it applies; if the dashboard window is unbounded `all`, Reliability keeps an independent labeled 7d cutoff because a rate without a range is not actionable. Like every other panel it states a cold load and a failed read in place (a failed read also turns the connection line to "panel update failed"), and a window with no settled runs says so instead of drawing a blank chart. Half-open cutoffs (`since ≤ t < until`) from ORB-10609 are unchanged.

Run Detail > Steps now includes compact per-step agent log expanders for CLI-backed activity steps [T20260508-14]. The UI renders bounded stdout and stderr previews from `/api/runs/:id/logs`, distinguishes stderr blocks from stdout blocks, highlights structured `ERROR <target>:` lines, and keeps blob references behind the API so operators do not need to resolve content hashes manually.

Health's Errors view combines Orbit process ERROR events with structured agent stderr. Step completion rows join the owning run's audit step to show its failure message and link to that step. The process log is host-global, so a run-affiliated row whose run belongs to another workspace is omitted from the selected workspace's view (it appears under the owning workspace); rows with no run affiliation stay. Repeated event IDs collapse into one row; distinct stderr lines from one invocation remain together in its message. Targets appear as a column, worktree prefixes are shortened with the full message available in the title, and Codex patch-verification retries (`codex_core::tools::router`) and model-manager timeouts (`codex_models_manager::manager`) live in a collapsed Agent diagnostics section. Errors requests the shared dashboard window and labels that range and the row cap; when log retention or the stderr read cap leaves the start of the window unread, the Errors header adds "covers since" with the instant its rows actually cover. Incidents defaults to unexpected failures. Each of its five class tiles counts its class's incidents, events and runs in the window and requests that class before the row limit is applied; the selected tile is visibly selected and exposes its pressed state within a named group. There is no mixed-class list, so newer refusals never push an older unexpected incident out of the limit. The header labels the newest shown incidents out of the matching total.

Health › Metrics is a full-width view over the shared window; its own window selector writes the same scope [ORB-15746]. The trend card has two tabs. **implement_one duration** plots the average, p50 or p95 wall-clock time of the implement_one runs that finished in each bucket as four lines: all runs, then the low (Easy), medium and hard complexities. xhard and unset runs count toward All only and stack as `other` in the runs strip under the plot. A bucket value from fewer than three runs is drawn hollow, with an amber count in the tooltip, and a bucket without runs breaks the line. **Tasks completed** stacks the tasks that reached done in each bucket by complexity, under a total line; rejected and archived counts appear in the tooltip and the table. The series cards are both legend and toggles: each shows the window value and its change against the previous window of the same length (`all` has none), and the last visible series cannot be hidden. Chart and Table show the same buckets, the table newest first, and a focused chart steps through buckets with the arrow keys. Buckets are clock-aligned: 5 minutes for 1h, 1 hour up to 2 days, 6 hours up to a week, 1 day up to 60 days, then weeks from Monday. Buckets narrower than 6 hours read in the browser's zone and wider ones in UTC. An empty window offers the next wider one. Below the trend sit implement_one by actor for the window (runs, average, p50, p95, change in average and a per-bucket sparkline), the slowest runs with task links, actors within one complexity over the last 30 days (bar = average, tick = p95), and outcome by complexity for all time. The Step metrics table and the summary card beside it were retired with this view.

Diagnostics has an Incidents sub-tab after [ORB-10871]. A raw failed audit row is evidence, not an incident: one refusal repeated in a burst is one problem, and one failed run that propagates its failure up through its enclosing steps is one root cause with a chain beneath it. `/api/audit/incidents` groups the window's failed and denied audit rows by `(job run, signature)`, where the signature is `class | actor | surface | normalized message` and volatile tokens (paths, ids, numbers, timestamps, hashes) are replaced with placeholders; same-run clusters of the same class within a 60s cascade window collapse onto their earliest cluster, which becomes the incident root, with the rest recorded as its propagation chain. After [ORB-10969], a later incident whose raw message cites another incident's `job_run_id` (the parent/child `pipeline_success_guard` pattern) also folds onto that cited root, so one failed leaf is one incident with its cascade count rather than independent roots. Grouping reads only durable audit columns, so no tool, agent, workspace, or task is special-cased.

The list then rolls incidents that share a signature across runs into one row [ORB-15221]. A row is titled with the first line of its message and reads surface · actor · cadence. The cadence appears when the gaps between fires are regular (`every 20 min`); a wider spread is qualified (`about every …`). A row with no recorded message reads `<surface> failed; no message recorded` and is flagged `no message`: the grouping signature is never shown as a message. The count column gives the number of distinct runs for a recurring signature (the incident count when no run id was recorded) and the event count otherwise. Every row draws its first-to-last sighting on one axis spanning the selected window (`24h ago · 12h · now`). A lifespan narrower than 1% of the axis is a dot, and a signature seen within the last hour is drawn brighter, with its last-seen time highlighted. Rows sort by last seen, and the class is not repeated on each row. Incidents with no signature stay separate. The rollup uses the incidents the panel received; when the header says the list is the newest N of a larger match, the run count is among those N and the footer offers Load older, up to 200.

One failure is often recorded at several surfaces — a parent's wait, the worker that ran the step, a guard — each with its own signature. After [ORB-15434] every incident also carries `cause: {key, label, basis}`, derived from its root's structured evidence by shape alone, with no tool, job or workspace name special-cased. The step is the last backtick-quoted name introduced by `action`, `step` or `activity` on the message's first line (the innermost of a nested chain), else the row's `activity_id`. The code is the first `kind=`, `code=`, `error.code=` or `error_code=` value after that step on the same line, else the first `[compound_tag]` opening a message segment; a tag needs `_` or `.`, so a log level such as `[error]` is not one. Within one class, incidents share a cause when they name the same step and code (`basis: step_code`), the same step and the same normalized first line after it (`step_message`), or, with no step, the same code (`code`). Two codes under one step are two causes, since a code is its producer's statement of which failure occurred. With no step and no code the cause is the incident's own signature (`signature`), so nothing merges without evidence. The key is a stable hash of the class, basis and that evidence, so a refresh over the same events returns the same key. A signature row takes the cause of its newest incident.

The list groups by cause by default. A cause with several signatures gets a header showing the newest signature's title, the cause code, `N signatures · first … ago`, one lifespan mark per signature on the shared axis, `N sigs` and the last sighting. Its signatures are indented below it, newest first. The header is a label, not a control, and counts signatures only; runs and events stay on each signature row and are never added across them. A cause with one signature is that row alone, with the cause code beside its title. The By cause / By signature segment (buttons with `aria-pressed`) switches to the flat list, which names a structured cause after surface and actor, and the selected signature is kept. Search also matches the cause code.

Above the list, a 1h/6h/24h/7d control picks the window. 1h, 24h and 7d set the shared dashboard window; 6h exists only here and lasts until the shared window next changes. One line restates the window's incidents, failed events and runs against its audited events. Insight chips narrow the list to signatures that failed in the last hour or that record no message, and a search box matches the message, surface, actor, step, and run or task ids. Selecting a row fills the detail panel, which stays in view beside the list while the list scrolls and stacks below it when the panel is narrow. It shows class and live or quiet pills, the title, one summary sentence, and the lifespan on a wider axis. Below those are the surface, actor, step, count, first and last seen, and the cause code (`none recorded` when the cause fell back to the signature, with the grouping basis in its tooltip), then the full wrapped message with a Copy button. It lists up to five other signatures with the same cause under "Same cause, other signatures", headed by the basis that grouped them (for example "Grouped by the same step and message: action `candidate_validate`"). It then lists up to five signatures that share the normalized message but not the cause, and each run with its own incident id and run and task links. A stored message ending in an ellipsis was cut before it reached the incidents feed. Unless one of its audit events kept the whole text, the panel says so and links those events. The feed itself bounds every message it carries (see the list-message cap below); for a message it cut, the panel shows the excerpt and a Load the full message button that fetches the text from the audit row named by `message_event_id`, and Copy then copies the whole message. View run (or View runs) and Audit events link out; Audit events uses the exact event ids when the payload carried all of them. The panel has no repair-task action, because the dashboard has no guarded path for proposing a task. The row keeps the actor recorded on the audit events. A clock-started routine still shows that actor, because the payload does not identify the scheduler separately.

Three counts are always rendered together with the selected window — raw failed events, grouped incidents, and affected runs. Each class tile reads `N incidents` over `M events · R runs`, and the line below the tiles restates the window's totals against the audited-event denominator. Failures stay classified as policy denials, expected refusals (an `OrbitError`-derived caller-input refusal, with the internal class label in a tooltip), or unexpected failures; classes are counted separately and never merged into one incident. Deferrals — a provider usage limit, or a run that deferred its work to a later one — have their own `deferred` class, labelled "deferred, not failed", with its own class tile [ORB-15517]. Audit > Failures by tool after [ORB-10969] excludes rows with no tool identity from tool denominators and rates (they are not a synthetic tool named `unknown`) and labels them as `job-run lifecycle` beside the tool cards. The scoreboard shows failed / total calls beside incidents / failure events, with the internal metric names in tooltips, so a burst can no longer inflate an agent's apparent failure rate. Nothing is dropped: the detail panel's audit evidence holds the grouping signature, the propagation chain and every underlying audit row the payload carried, and links back into the raw Audit view, which still returns every event. Labels and denominators wrap rather than clip, and a 375px phone does not scroll horizontally.

List projections bound their message text after [ORB-15527]. A failed validation can record a message of a few hundred KB, and the incidents feed copied it into the incident, each of its events and samples and each propagation link, while the Errors and run-friction feeds copied it into every row on every 30-second poll. Each `message` in `/api/audit/incidents` and `/api/diagnostics/errors`, and each `stderr` in `/api/diagnostics/friction`, is now redacted in full and then cut on a character boundary to at most 2048 bytes (`LIST_MESSAGE_MAX_BYTES`), so a cut cannot leave part of a secret unredacted. The object that carries a cut field has `truncated: true` (`false` otherwise); the payload-level `truncated` on incidents still means the grouping scan limit. The full text stays reachable. `GET /api/audit/events/:id/message` returns one audit row's whole failure message, redacted the same way, and the incidents detail panel loads it on demand. Loaded messages belong to the selected host and workspace: switching either clears the detail cache, and a response from an earlier scope or visit cannot change the displayed message or its Copy value. An Errors or friction row links its run, whose step error and run events keep the whole message, and an Errors row with no run says the process log keeps it.

Diagnostics no longer has a Friction sub-tab after [ORB-00060]. The Friction name is reserved for append-only `.orbit/frictions/` artifacts, while audit-derived negative run signals stay visible in Recent Runs. Recent Runs joins `/api/job-runs` with `/api/diagnostics/friction` client-side by run id (`run_id`/`job_run`) and keeps the table sortable across `denials`, `tool fails`, and `duration`; the duration cell can carry the long-run flag when the diagnostics source supplies one. This preserves column continuity with the existing compact dashboard telemetry direction from [T20260428-15].

Run list responses (`/api/job-runs` and `/api/job-runs/all`) and the `run` object in `/api/runs/:id` include nullable `task_ids` and `tasks` fields derived from persisted run input. `tasks` contains `{id, title}` labels; a missing task retains its ID with a null title, and a run without task input has null fields. Each workspace list resolves titles through one metadata listing, with no task-body reads per run. The Runs Task column links each ID and truncated title to the task in its workspace, including completed tasks. Run detail shows the same task labels in its header and on coordinator child-run entries.

Run detail joins each `child_dispatches` entry to its child run in that same response, adding nullable `state`, `started_at`, `finished_at` and `duration_ms`. The child list shows state dots, outcome labels, durations (elapsed while running), and a tally of every admitted child's current outcome. Active children appear first, followed by failed or held outcomes, successes and cancellations; failed and cancelled rows use distinct state colors and every child links to its run detail. The dispatch checkpoint stays visible as secondary context. Unreadable child runs show unknown state and unavailable timing, never the checkpoint's stale outcome. These fields refresh with the ordinary run-detail poll, including after the parent finishes. A failed, timed-out, or interrupted run's failure box links every run id and task id in its message, and names the deepest failed or cancelled descendant as `Root cause: <run> <state> at <step> - <message>` when that descendant exists. A cancelled run shows who cancelled it, when, and the recorded reason, or `no reason recorded` when the cancel record has none [ORB-15211].

The `/api/diagnostics/friction` projection is memoized per workspace runtime, month and bounded row limit for 15 seconds, sharing one computation across overlapping Runs refreshes. Audit-derived CLI failure rows include an stderr excerpt: an 8 KiB prefix of the blob is read and redacted, then cut to the 2048-byte list-message cap, with `truncated: true` when the cap binds or the blob is longer than the prefix [ORB-15527]. Every other friction row's `stderr`, including legacy JSONL entries, is bounded the same way. Missing blobs produce empty stderr; the legacy friction JSONL remains the preferred source when it has rows.

Knowledge is a top-level dashboard tab for friction triage. The retired native learning panels, routes, metrics, and mutations were removed by [ORB-10736].

Knowledge detail panels stay pinned while the artifact list scrolls after [ORB-10444]. The list grows well past a viewport, and scrolling it used to carry the pane the operator was reading out of view. The detail panel is sticky below the fixed chrome (header, tabs, health strip) and bounded to the remaining viewport height, so detail content taller than the screen scrolls inside the pane rather than being clipped. The single-column breakpoint unpins it, where the pane already stacks below the list.

## 5a. Audit › Codebase

Audit has two views, Events and **Codebase** (`#audit/codebase`); Codebase replaced the Policy view [ORB-15355]. It ranks which parts of the repository are expensive or risky for agents to change, from records Orbit already keeps. It is read-only and scoped to the selected workspace; the aggregate view shows the usual placeholder. The hash carries the view's selection (`#audit/codebase?window=30d&min_support=5&rollup=dir`, defaults omitted), so a reload or a shared link restores it, and visiting Codebase leaves the Events filter as it was.

"Touched" means a task's **declared footprint** — its `context_files` plus the selectors `context_files_widened` added — not the diff that landed; a disclosure under the view's one-line purpose says so. Attributing a ranking to the landed diff is out of scope. The header's meta line gives the tasks scanned, when the scan ran and that it is recomputed every five minutes. The controls are segmented buttons with `aria-pressed`: a window (7d, 30d, 90d by default, or All) and Group by (File; Directory, ending in `/`; or Crate, where `crates/<name>/…` rolls up to `crates/<name>/` and any other path to its top directory; files at the repository root roll up to `./`), plus a **Min. tasks per path** stepper for the minimum support (the smallest denominator a ranked row needs, 15 by default, at least 1; the stepper walks 1, 2, 3, 5, 10, 15, 20, 30, 50, 100). Every ranking shows its rate with its numerator and denominator, ranks by rate, then numerator, then path, keeps the top `row_limit` (25) rows, and states how many rows fell below the minimum support. Each ranking has an empty state; an empty workspace answers empty sections, not an error.

Codebase takes the full width: the Audit summary panel describes audit events, so it shows beside Events only. Below the header are seven **ranking tiles**, each a button with `aria-pressed` that opens its list: **In several rankings** (the default), Regressions, Footprint misses, Blocked by a run, Rejected after a run, Change coupling and Lock contention. A tile's headline is the top rate and the top path's base name, a count, or None; its footer gives the ranked count and the below-support count. Blocked adds the unclassified block count as a warning; Rejected leads with the tasks rejected after a run and the most on any one path; Lock contention shows a good state when no lock was refused.

- **In several rankings** lists, client-side, the paths in two or more of the four path rankings (regressions, footprint misses, blocked, rejected), by how many, then by the highest rate outside Rejected, whose one-off rejections would otherwise lead. Each path has one chip per ranking with its rate and n/d. At crate grouping a hint says that nearly every crate clears the threshold, so the list says little there.
- **A path ranking** lists rank, the path (directory dimmed, base name bright; it wraps and is never truncated), a rate bar, the rate and "n of d". Chips name the other rankings the path is in; widenings beyond the task count and blocks with no recognisable cause show as extras. The footer gives the below-support count, with **Show paths with 5+ tasks** while the minimum is above 5.
- **Blocked** adds a stacked bar and legend of `blocked.causes` — run failure (counted against paths), unclassified and each infrastructure cause — and, when unclassified is the largest share, a warning that the rates only reflect run-failure blocks. **Rejected** adds `rejected_with_run`, `excluded_without_run` and the most rejections on one path, and calls the list weak evidence when that is 2 or fewer.
- **Change coupling** rows are two-line pairs with a Jaccard bar. A directory paired with its own `tests/` child is tagged as expected, and **Hide expected pairs** removes those. With no pair ranked, the empty state names the below-support pair count and the large-reservation exclusion and offers **Group by directory** and **Lower to 5**, which change the selection and rewrite the hash.
- **Lock contention** with no row, nothing below support and no denial in the window says no lock was refused, with the window's reservation count. The view always notes that lock wait time is not recorded.

A **detail panel** sits beside the list (below it on a phone) and shows the selected row, the list's first by default. For a path it gives the path, **Copy path**, and its place in each of the four rankings ("#n of N", or "not in the top `row_limit`"). When the path ranks for regressions it lists the regressed tasks (three, then **All N**), each with its task link, crew, title and the tasks that named it in `regression_from`; a task that regressed five or more of the ranked regression paths, counted client-side from the rows' `regressed_tasks`, is marked with that count, since one fix there lifts several rows. Regressions by crew follow, with a note that crews take different complexity tiers. The task list has no path filter, so the panel offers no "tasks that declared it" link. A coupling pair shows both paths, the Jaccard rate, "reserved together n of d" and each path's own reservation count. The tile, the row and the other view choices are not in the hash; every part of the view is a keyed node, so a 30-second poll that answers the same payload changes nothing on the page, keeping the tile, the row, the open disclosure and the scroll.

| Change coupling | Jaccard overlap of file reservations: reservations holding both paths ÷ reservations holding either | Reservations of more than 12 files are excluded and counted; pairs held together fewer than the minimum support are omitted. |
| Blocked | tasks blocked by a run failure ÷ tasks that touched the path | Infrastructure causes — auth, sandbox, disk, provider limit or outage, an interrupted run — are counted by cause and not against files. A block with no recognisable cause is its own `unclassified` bucket, both overall and per path. Auth, disk, sandbox and provider classification require a typed provider failure or a concrete failure diagnostic; a test or module name mentioning those components remains a work failure. |
| Rejected after a run | rejected tasks that had a job run ÷ tasks with a run that touched the path | A rejection at proposal, with no run, is excluded and counted. |

`GET /api/codebase/analytics?workspace=…&window=…&min_support=…&rollup=…` answers one JSON object: the six sections (`regressions`, `lock_contention`, `footprint_misses`, `change_coupling`, `blocked`, `rejected`, each with `rows` and `below_support`; `lock_contention` also carries the window's `reservations` and `denials` totals) and `window`, `since`, `min_support`, `rollup`, `touched: "declared_footprint"`, `computed_at`, `cache_ttl_seconds`, `tasks_scanned` and `row_limit`, the rows each ranking keeps. An unknown window or rollup, or a zero minimum support, is a 400. The server scans each task's history, the reservation history and the lock denials once per workspace runtime and keeps the facts for five minutes, single-flight; the window, minimum support and rollup only slice those cached facts, so neither the 30-second poll nor a control change rescans task bundles. A ranking may therefore lag the records by up to five minutes, and `computed_at` says when the scan ran.

## 7. Task Write Actions

The task list groups by status in the order a person has to act: **Awaiting approval** (`proposed`), review, blocked, in progress, backlog, then the closed statuses. Each group is a card: its heading names the status with its dot and count and says what the group is waiting on, and its own column heads follow. The blocked card sits on the danger wash. The status chips above the list count their tasks when the loaded page is the whole match; the closed statuses, All and Not ready sit after a divider as quieter text chips. Statuses with no tasks are named in one line above the cards (`Nothing in review or blocked.`) instead of drawing empty cards. Each row carries the one action its group needs, at the row's right edge: **Approve** on a proposed task to move it to Backlog or a review task to close it as Done (`POST /api/tasks/:id/approve`, the detail's approve; a distributed review handoff uses its candidate-scoped approval instead), **Ship** on a backlog task (the same one-click ship and duplicate-dispatch guard described below; it takes the accent when nothing holds the task), and **View run** on an in-progress task with a navigable run. Review rows keep their pull request link beside Approve; their approval requires a selected workspace and is disabled in the all-workspaces view. Approval shows a pending state and moves the row only after confirmation and a list refresh. A failed row action shows the server's reason under the button and keeps the row. A title stays on one line and is cut with an ellipsis, so every row has the same compact height; the row's tooltip carries the full title and the title button keeps it as its accessible name. Only `os:` tags show as badges on the title; a leading `[source]` bracket reads as muted title text. Crew reads as a compact mono chip; clicking or tabbing to it reveals its native select in the same cell, preserving keyboard editing without an extra Tab stop or a layout shift. Status is edited in the expanded detail's properties, where a successful change keeps the detail open. In-progress and blocked rows add a **Host · running** column: the machine the run is on (the selected host when the run is local), how long it has run (from `/api/job-runs?state=running`, at minute resolution) and how many files the task holds locked (from `/api/tasks/locks`); the group heading totals them (`9 on dk-server-2 · 34 files locked`). Every row keeps a 72px action column so titles and controls line up between groups; when no visible row has an action (a Done-only or Someday-only view) the list gives that column back to the title for all rows at once. Narrow panels place the controls on a second line below the title, which stays on one line. The task id in a row (and the run id in the Runs table) is a real button that copies it: Tab reaches it, Enter or Space activates it, it keeps its own focus ring, and its `copied!` / `copy failed` result is announced instead of only flashing.

The Tasks tab is writable for the actions that otherwise force a context switch to the CLI [ORB-10444] [One-Click Task Ship and Human-Attributed Dashboard Comments](./4_decisions.md#one-click-task-ship-and-human-attributed-dashboard-comments).

**Ship** appears on `backlog` tasks and is one click with no configuration UI: it posts only the task id to `POST /api/workflows/ship`. The crew is resolved by the pipeline from the task's own record and the mode from the selected workspace's registry binding, so that endpoint's omitted-`mode` default is the workspace ship mode (falling back to `pr` for a runtime with no binding). The resulting run id and state are surfaced as a notice, and a failed dispatch shows the server's error text instead of silently no-opping. Duplicate dispatch is refused: an explicit task selection whose id is already carried by a non-terminal run answers `409` with code `ship_run_in_flight` naming that run, and the UI holds a per-task guard across the double-click window. That refusal is the shared ship submission path's typed conflict, not an endpoint-local policy: the MCP tool, routine action, and interactive CLI all refuse the same duplicate ([ORB-10631], [Ship duplicate-dispatch guard lives in the shared submission path](../activity-job/4_decisions.md#ship-duplicate-dispatch-guard-lives-in-the-shared-submission-path)).

**Comments** post to `POST /api/tasks/:id/comments`, which writes through the task's existing review-thread structure rather than adding a field to the task record, so a comment survives a reload like any other task history. Authorship is forced to a human identity: an absent, agent-family, or model-constant author collapses to the `human` label, because the dashboard process may itself run inside a managed Orbit run where the runtime's ambient actor is a model.

Inline status/crew edits show a pending state on the control, refuse a duplicate submission while one is in flight, and report durable success or exact failure text next to the control (a live region, so the same feedback reaches assistive tech) rather than only logging to the console. The status control exposes every other existing status for every task, including reopening `done`, direct archival, and restoration from `archived`; the PATCH is an audited classification edit and never launches, cancels, merges, or completes work by itself. A move into `backlog` can make the task eligible for a later configured automation sweep. A successful edit offers a bounded-window undo that restores the prior value with one click, expiring automatically once the window (or a further edit) makes restoring it unsafe [ORB-10874]. Status lives in the expanded detail and rows group by status, so a successful status change from the detail folds it in (the `open=` URL parameter no longer names the task). Its success feedback and undo move to the collapsed row for the rest of the undo window, or to a notice above the list when the new status is filtered out. Undoing from there keeps the row folded. A failed, cancelled or refused change leaves the detail open with its feedback beside the control, a pinned detail stays open, and a status change that arrives through a refresh never changes which rows are open.

The expanded task detail edits five more fields in place [ORB-12235]. **Complexity** is a `low`/`medium`/`hard` select with the same pending/saved/error feedback and bounded undo as the crew select; `unassessed` is deliberately not offered because the update endpoint rejects it, and a task already carrying it keeps a disabled placeholder so the select still shows what is stored. **Description**, **tags**, **acceptance criteria**, and **context files** each render their read-only view with an `edit` affordance that swaps in a text editor carrying Save and Cancel. A save sends only the field it edited — a whole-object PATCH would clobber whatever an agent wrote concurrently — and Cancel restores the view without a request. A refused save keeps the editor open with the operator's text and the server's own reason beside it; for context files that reason is the selector-existence refusal, which the editor's `allow missing context` checkbox answers for a selector naming a target the task will create. An open editor holds its detail node through the background refresh the same way a half-written comment does, so a poll never discards unsaved text.

In the aggregate ("All workspaces") view there is no ambient workspace to scope a mutation to, so every inline edit — status, crew, complexity, and the field editors — is refused unless the task carries its own `workspace_id` (present on every `/api/tasks/all` row), in which case the mutation is sent explicitly qualified to that workspace rather than the currently-selected one [ORB-10874] [ORB-12235].

## 7a. Task Comment Thread

Comments are the dashboard's long-form channel — agents post spec-length Markdown — so they render as a document rather than a log line [ORB-12645]. The thread is its own panel spanning both detail columns below them, not a cell in the narrow side column, and each comment is a card: a 28px initial chip, the writer (an agent or crew name in the accent color with an `agent` pill beside it, a human in the foreground color), absolute and relative time, and `raw` / `copy` / `#` actions. `raw` swaps the rendered body for the Markdown it was written in, `copy` takes that source to the clipboard, and `#` scrolls to the comment and copies a link carrying its anchor. Bodies render through the same `renderMarkdown()` wrapper as every other dashboard-authored body, so sanitization is DOMPurify's and a comment carrying a `<script>` or an inline style renders inert.

A body taller than about 300px is capped behind a bottom fade, with its word count, its `##` section titles, and a **Show full comment** control; the panel header carries a `collapse all` beside the count. Height is estimated from the source rather than measured, because the detail is built off-document and a measuring pass would paint the thread a frame late. An expanded card keeps its header on screen while the body scrolls, and a body with three or more `##` sections gets an *In this comment* outline beside it, built from the rendered headings and tracking whichever section is in view. Expansion, the raw/rendered toggle, and the newest/oldest thread order are operator state rather than task data: the first two are held per comment so the 30 s refresh that rebuilds a detail restores the thread as it was left, and the order persists in `localStorage` like the other presentation preferences.

The composer says what it accepts: the field is labeled **Add a comment**, its placeholder and hint line name the marks that carry, and a `preview` toggle renders the draft through `renderMarkdown()` before it is posted. The write itself is unchanged — still `POST /api/tasks/:id/comments` with the message alone. Counts, section lists and the outline are computed in the browser from the rendered body, so no API carries them. The history panel is untouched, including its filtering of legacy bare `commented` stubs.

Task-pilot comments with a valid `operation_id=<64 hex>` receipt and assessment JSON render labelled disposition, confidence, recommended crew and complexity, and rationale fields. Recommendations show their prior value when the receipt provides a changed value. Evidence gaps, reassessment triggers and blockers appear as lists; duplicate and already-landed findings appear when present. The raw control and copy action retain the original receipt text. Malformed or unrecognized assessments retain the normal comment rendering. `orbit task show` and its text comments projection use a one-line assessment summary, bounded to 150 characters before the timestamp and author; their JSON projections retain the full original message. These are presentation changes only: storage and re-pilot receipts are unchanged.

## 8. Task Count, Filters, and the Tasks/Log Layout

The Tasks count uses the `/api/tasks` or `/api/tasks/all` paging envelope (`{ items, total, limit, truncated, offset, next_cursor }`) to render the current page range and matching total rather than an ambiguous `N/50`. For example, a page with twenty items at offset zero of fifty-five matches reads `1–20 of 55`; the final fifteen-item page reads `41–55 of 55`. An empty page reads `0 of N`. If a client-side filter narrows the loaded page, the count prefixes that range with the number shown, such as `3 shown · page 1–20 of 55`. The count does not name a server page limit or describe a fetched-versus-filtered relationship. The active status chips are sent to the server as an explicit `status=` filter rather than fetched wholesale and narrowed client-side, so the envelope's `total` describes the filter actually in effect [ORB-10874].

A list row is a *summary* (`"projection": "summary"`) rather than the full task [DANI-10391]. It carries the fields the collapsed row renders and filters on — id, title, status, priority, complexity, type, tags, crew and the registry-resolved `resolved_crew`/`crew_model`, timestamps, attribution, dependencies, relations and context selectors — plus `comment_count`, `history_count` and `artifact_count` in place of the comment, history and artifact bodies, and no `description`, `plan`, `execution_summary` or `acceptance_criteria`. Its `status_transitions` name the governed targets without their `required_field`. Expanding a row reads `GET /api/tasks/:id`, which serves the full projection (bodies, sidecars, review gate, run-aware crew, and each transition's evidence requirement); the row shows a polite loading placeholder on its first read, keeps the last read painted across the 30 s refresh while a fresh one is in flight, and offers an in-place Retry when a read fails. A governed status change from a summary row reads the detail first so the evidence prompt follows the requirement the server actually holds; a forced (off-table) change needs no read. Server-side, the list page builds the crew registry once per request and issues no per-row job-run or review-ledger lookups.

Proposed and backlog rows, list and detail alike, carry `readiness: {ready, gaps, preparing}`; other statuses omit it. Each gap is `{code, severity, message, fix}` from the same orbit-types rule drain approval and backlog admission apply, so the dashboard never disagrees with the drain: `missing_context_files` blocks a proposed task and is advisory in the backlog, where its message names the missing file lock and the multi-slot wait (the same text CLI and MCP task writes return as a warning), `unassessed_complexity` blocks both, and a `no-diff-expected` tag clears both. These gaps cover only what an edit fixes; waits that clear on their own (dependencies, locks, host OS, crew, provider backoff, a red base) come from drain readiness, below, which leads the same detail card. `preparing` is true while an active task-pilot run holds the task; the list reads those runs once per page. The row shows a chip in the `os:` badge slot: amber `not ready · N` when a gap blocks, muted `advisory · N` when every gap is advisory, a dashed `preparing` while a pilot prepares it, and nothing for a task that lacks nothing. Its tooltip lists each gap. The detail's **Readiness** card lists each gap after its drain headline (below), blocking gaps first: each is a grid row with the same severity chip as the row (blocking in the amber pending colour, advisory muted) in a fixed first column, and its message and `Fix:` line share the second column's left edge. A **not ready** chip after the status chips narrows the loaded page to tasks whose `ready` is false; it is client-side because readiness is derived rather than stored, and it travels in the hash as `ready=not`.

Why a backlog task is or is not starting comes from the drain readiness snapshot the Drain card reads (`GET /api/workflows/auto/readiness`), shown on the task itself. A dot beside the task id names its pool, the same four the drain admits by: **Eligible now**, **Waiting on locks** (a context lock, a group member, a same-wave deferral, a live child's claim), **Waiting on capacity** (no free slot, a host throttle, a scheduled shutdown, stopped admissions) and **Waiting, other** (host OS, provider limits, dependencies, crew and the rest). Its accessible name gives the pool and the wait (`Waiting on locks: waits on ORB-77 · lock`) and its title adds the server's detail and reason. Above the backlog rows a readiness strip draws the pools as one bar with a legend of counts; a legend entry is a pressed-state button that narrows the backlog card to that pool, and a task missing from the snapshot is counted beside the legend. Without a snapshot, or after a workspace change until the next one arrives, rows carry no dot and the card draws no strip, so a stale wait is never shown against another workspace. The detail of a proposed or backlog task asks for its own entry with `GET /api/workflows/auto/readiness?task=<id>` (a comma-separated list explains exactly those tasks, like `orbit run readiness <id>…`; an unknown or malformed id is a 400), so it answers without the Drain card and for a task past the snapshot's bound of 50; until that read answers, or if it fails, the Drain card's snapshot entry stands in. Its **Readiness** card leads with the same words as the dot, from one shared helper: the pool, then the badge text (`Waiting on locks` · `waits on ORB-77 · lock`, `Waiting on capacity` · `no free slot`, `Waiting, other` · `base red`, `waits on deps`, `needs macos host` or `awaits approval` for a proposed task). Under it come the specifics: the holder task or live run as a link, the contested selectors, each unmet dependency linked with its status, the server's `detail` (a red base names its command and base sha) and the raw `Reason: <code>`; an unknown reason still shows its code and detail. The preparation gaps follow in the same card. **Ready: nothing is missing.** appears only when readiness reports the task `eligible: true` and it has no gaps; without an entry the card says the drain readiness is unknown (or still being checked) and claims no pool.

The Tasks pager has Previous and Next buttons. Previous follows the saved cursor history and is enabled after moving beyond the first page; Next follows `next_cursor` when the server supplies one and is disabled on the last page. Both controls are disabled while a page is loading. The adjacent polite live region reports `Loading task page…` or `Page failed: …`, and changing the status or search filters resets pagination to a new first-page request.

The active status filter and search query are represented in the `#tasks` hash (mirroring the Audit tab's own hash-encoded filters) and restated as text for assistive tech beside the count, so the current view survives a reload or the browser's back/forward button and is legible without reading each chip's color. The task a person has open is in the hash too (`open=<id>`), so a copied URL reopens it. Every task link in the dashboard (Runs, run detail, log rows, Errors, Jobs) is `#tasks?open=<id>` with the host, workspace and window in the query: it names no filter, so following it leaves the chips and search as they were, shows a task the filter hides pinned above the list, and adds a single Back step. The selected workspace is likewise mirrored into the page's `?workspace=` query parameter on every change [ORB-10874].

## 8a. Task Artifact Previews

Artifact rows in task detail stay one compact line — path, media type, size — and fetch a payload only when clicked, so a task carrying a screenshot is no more expensive to scan than any other [ORB-11365].

A supported raster artifact (`image/png`, `image/jpeg`, `image/gif`, `image/webp`) renders as an actual image rather than a download link. The preview scales to the detail column (`max-width: 100%`, `height: auto`) so it never forces the panel to scroll sideways, and it is never upscaled past its own resolution. Below 760px it takes the full column width and is capped at `60vh` so a tall screenshot cannot push the rest of the task off screen. A checkerboard background makes a transparent PNG read as transparent instead of as whatever the panel happens to sit on. Each preview carries Open (new tab) and Download controls, and the artifact path is the image's alt text — it is the only description the artifact has.

When the browser cannot decode the bytes, the preview says so and still offers the file, rather than leaving a broken-image icon.

The set of types rendered inline mirrors the server's `nosniff` allowlist exactly. `image/svg+xml` and `text/html` are absent from both: they are viewable formats that are also script hosts, so they stay downloads. Everything else keeps its existing text render or download link.

## 9. Operations

Operations renders routine-definition state separately from the host sweep clock [ORB-10875]. Each routine row names its source workspace, cron schedule, catalog target, last scheduler evaluation/fire, linked run outcome, and next due slot. Definition `enabled` is the versioned switch; the clock card independently reports its native provider, configured/effective cadence, loaded/active health, and native last/next tick values when available.

Routine toggles require one concrete workspace; clock controls also require the exact local host returned by the status response, because the clock is host state while a definition is not [ORB-12236]. All-workspace mode stays readable but has no active controls. Each mutation carries its displayed target plus expected prior state, so a delayed or duplicate click conflicts instead of overwriting a newer observation. The routine write boundary rereads the definition and refuses a file retargeted since selection, and every authorized refusal is audited as a failed operation rather than a success. The UI also holds an in-flight guard, renders pending state, and reports the server's exact success or failure. Starting/stopping the native service requires confirmation; cadence is a separate control and its feedback explicitly preserves the service-state distinction. The backend accepts typed actions only and resolves routine paths and native commands itself—browser input is never interpreted as shell text.

The Jobs pane combines routine targets with recent job runs. An operator session can use **Run** on a sweep or other no-input catalog job; `POST /api/jobs/:id/run?workspace=…` resolves the id from the catalog only, records dashboard provenance, and returns the run id and queued/submitted state. A file with the same name in the server's working directory cannot replace the catalog definition. The CLI's `orbit run job <path>` continues to accept direct YAML paths. The pane shows the receipt or server error and refreshes recent runs after submission. Pausing a routine does not disable manual Run. Delivery jobs stay disabled in this no-input UI because they need a task id or delivery window; use Ship or Drain. Read-only sessions see the authorization reason, and each job retains a copyable CLI command.

**Replay run** uses the same `job.run` operator capability and requires an explicit workspace. `POST /api/runs/:id/replay?workspace=…` accepts an optional `claim_token` body field, checks workspace and drain admission, and returns `{run_id, state}` as soon as a detached replay is persisted. The Runs view navigates to that run for progress while every step executes again against the current catalog definition. Recorded `completion: done` input also requires the completion capability; a read-only session cannot reuse that authority by replaying a historical run.

Run detail's Events tab opens on the newest page, in chronological order, and labels the displayed range and total count. **Load earlier** pages backward; **Newest events** returns to the end. Refresh preserves the selected page's distance from the tail. Event times include seconds and the local time zone, with a date on the first row and each day change.

The step timeline reads retry markers independently of the selected Events page, so paging does not change its markers or Retry legend. Refresh reloads that run's retries in the selected workspace; changing run or workspace clears them immediately and discards delayed responses from the old scope. The projection shows the first 100 retries in chronological order and labels omitted later markers. A 404 retry read is treated as no retry markers, like a missing optional Events or Logs stream; other failed reads, including the bounded audit scan limit, show **Retry markers unavailable** rather than implying there were no retries. The filtered read scans at most 50,000 audit rows per refresh.

Steps show a loading skeleton until the detail read settles, a read error on failure, and an empty state only for a successfully loaded run with no steps.

`GET /api/runs/:id/events?tail=true&limit=N&offset=M` opts into `{events, total, offset}`. Offset counts rows backward from the end; each returned page is chronological. The count and page are scoped to the selected workspace and `v2_envelope` source, and both come from one SQLite read snapshot so a row that commits after the count cannot change which events the page contains. Tail pages do not support `kind`; requests without `tail=true` retain the existing oldest-first array response and kind filtering.

The two-column desktop layout stacks below 900px, and routine/clock metadata collapses to one column below 600px so schedules, state labels, and controls remain scannable at 480–720px widths.

The Tasks dock's Drain mode (`Drain | Log`) stacks three cards: the auto-drain status card, **Start a window**, and Locked files. Both drain cards project `GET /api/workflows/auto/readiness`. The status card's header carries the phase as a pill (Idle, Draining, Winding down, Pull drain or Read-only). Below it, a live window shows three figures — **Admitted**, **Still running** and, for a window started with approve-proposed, **Approved** with `approved_total` (whole window) and `held_total` (latest pass) from the payload's `approvals`, the hold reasons in its tooltip (without counts the figure reads `—` and its tooltip still names the opt-in) — then the coordinator run link and the time left, or **admissions stopped**. Then the workspace's leaf slots: `N of M in use`, free slots, a bar of one segment per slot (a continuous fill past 24 slots) whose overflow past the limit is hatched and whose accessible name reads `Workspace: N of M leaf slots in use`, an explanation of the binding admission constraint, and the slots held per pipeline. Host and provider holds follow as amber notes, then **Stop** with its help. Why each backlog task waits is not repeated here: the Tasks list shows it on the task's readiness dot and in the Backlog card's readiness strip (section 8), from the same payload. **Start a window** gives the eligible and waiting counts, then window length, parallel tasks, completion as two named options (**Stop at review** / **Mark done**) [ORB-12898], **Proposed tasks** as two more (**Leave for me** / **Approve qualifying**, the `--approve-proposed` counterpart), each with a line saying what the selected option does, and Start; it is hidden in a read-only view. **Approve qualifying** is off by default, carries the qualification rule in its tooltip (context files and an assessed complexity or the `no-diff-expected` tag, a clean task-pilot verification, `no-auto-approve` skipped), and names the opt-in in the confirm dialog. It posts `approve_proposed` to `POST /api/workflows/auto`, is governed as `auto_drain.approve_proposed` (operator session; the `403` carries that operation), and is disabled with a visible reason when readiness reports `controls_authorized: false` or `replica: true`, since a pull drain cannot approve. Locked files fold to one line per task (status, file count, short run id) with the paths behind a disclosure that stays open across refreshes. The throttle note states CPU as load per core (`load 1.6× cores`), the same reading and unit as the top bar's load reading. A provider-limit note names each reading in readiness `provider_limits` that gates admission: its window, use against the threshold, reset and the crews skipped; a task waiting with `provider_limit` shows that detail on its readiness dot [ORB-14698]. The admission summary names host shutdown, resource throttling, stopped admissions, workspace leaf saturation or task locks and live claims as reported by readiness; zero free slots alone never implies that a running task must finish. The workspace pipeline breakdown includes other occupied slots when legacy wrappers are absent from the pipeline map. Readiness is polled at the existing dashboard cadence on every tab. The dock tab stays labelled Drain while draining, with its live state in the accessible label and tooltip; Winding down remains visible beside the label, and the global top-bar indicator names the live state from any view. On a replica with a live pull drain and no owner window, the top-bar indicator shows its own dashed, accent-coloured **Pull drain** (or **Pull drain · admissions stopped**) state and the Drain tab's accessible label names it, never `idle`. The live window reads the server-stamped `ends_at` deadline, the coordinator run link, and its admitted and still-running figures from durable child lineage; it remains accurate after reload and across browsers. Stopped or expired admissions with live children show Winding down until the last child finishes. The indicators use text and color, announce changes through the card status line, and stop animating under reduced-motion preferences. Its controls are the dashboard counterparts to `orbit run auto`: **Start** submits a bounded window through `POST /api/workflows/auto`, and **Stop admissions** posts `POST /api/workflows/auto/stop` (`orbit run auto --stop`) with an optional `reason` and `claim_token` [ORB-12728]. The authorized Stop control is shown while readiness reports a live `drain_run_id` — or, on a replica checkout, a live `pull_drain_run_id` (`capacity.pull_drain_admissions_stopped` says whether its admissions are already stopped) — whose admissions are not already stopped. Its help explains that new tasks stop starting, existing tasks keep running, and completed results are sent to their owner. With no open window it becomes Send pending results for recorded results; a read-only view or missing operator authority (`--operator`, governed as `auto_drain.stop`) disables the control with a visible reason. The live coordinator is shown as a run link in the live window (a pull drain with no auto window reads **Pull drain**, with **admissions stopped** once stopped), the click confirms first and names each window it will stop (a pull drain's confirm says its admitted leaves stay claimed by their owner and that cancelling one fails its claim), and the response — `{ "workflow": "auto", "outcome": "idle" | "stopped" | "unchanged" | "cancelled_queued", "coordinators": [...] }` with each coordinator's outcome and still-running children — feeds the card's status line before readiness is re-fetched; that re-fetch neither announces the state change over the result nor replaces it with a failure if the read itself fails. Parallel tasks must be blank or a whole number from 1: any other value is flagged beside the field, left out of the readiness query, and keeps Start disabled. Stopping admissions is not cancellation: already admitted workers keep running under their captured completion authority, and cancelling one is the per-run cancel on its run detail page. That cancel's confirmation on a claimed follower leaf says it fails the claim on the owner and blocks the owner's task, naming that task: `GET /api/runs/:id` returns the leaf's `pull_claim` (the value `orbit run show` reports; `null` for every other run, and null when the admission cannot be read, with the failure logged), and a runs-list row, which carries none to avoid a per-row admission read, fetches that detail once when a claimed-leaf job's cancel is pressed. A pull drain's run detail also renders its `crew_window` from the same response: the runnable crews and each excluded crew with its source (`preflight` or `provider_unavailable`) and reason, mirroring the `Crews:` lines of `orbit run show` [ORB-13941].

## 9a. Plugins

The Plugins tab (`#plugins`) lists what `GET /api/plugins` reports for the selected workspace — each installed or pinned plugin's version, host state, workspace toggle, diagnostic, tools, and the Orbit version its conformance goldens last passed on — so a plugin that is disabled, missing or refused at load is visible *with the step that would fix it* rather than simply absent. Certification chips mark **behind host** when that version predates the serving host's `host_orbit_version`, comparing SemVer precedence and ignoring build metadata; absent or unrecognized versions do not establish lag. Operator sessions can enable or disable at host or workspace scope; host disable asks for confirmation because it affects every workspace. Host re-enable preserves previously recorded grants and program paths and refuses changed or absent consent with a CLI remedy. Installing, removing, upgrading and editing grants stay on the CLI, where the operator answers a manifest's permission request. Sessions without operator authority see no controls.

Panels are the one place plugin-authored data is drawn, and one generic renderer draws all of them: `kv` for an object, `table` for an array of objects (columns are the union of the rows' keys), `markdown` for a string, `json` for anything else, with an ill-fitting payload falling back to `json` rather than an empty card. Markdown goes through the same sanitizing wrapper task comments use, so plugin text cannot introduce script or event handlers. Each panel is read from `GET /api/plugins/<ns>/panels/<id>`, which executes only a tool the manifest declared a panel over, with no caller-supplied input; a panel over a mutating tool cannot exist, because `orbit plugin validate` refuses that manifest by name. `links[]` render as plain tiles that open in a new tab without handing over the opener. No plugin ships markup or JavaScript, so a newly installed plugin appears here with no dashboard edit [ORB-12738].
