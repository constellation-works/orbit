# Interpret delivery-refusal holds

## Delivery-refusal holds

A fail-closed delivery decision ends the run `held`, never `failed`. The
code comes from a typed refusal, never from matching diagnostic wording, so
read the code rather than the message text. Retry, step recovery, final
recovery and the failure handoff do not run for these decisions. The refusing
action keeps its existing task transition and landing evidence; run
finalization does not change the task's status. Gate and auto parents pass a
held child.

Run history lists the run as `held`, and reliability counts it
under held, outside the failure rate.

### Read the code on a run

```bash
orbit run show <run_id> --json
orbit run history --json
```

In the run-show response the code is the `run` object's `error_code`, with
the human-readable detail in `error_message` and the `held` outcome in
`run.state`. History lists the same run with a `held` state.

### Codes and next steps

Resolve the named refusal before starting a new delivery attempt. Apart from
`delivery_forge_observation_unavailable` (when the task stays in review) and a local `review_budget_exhausted`
(after an operator review reset), these holds do not enable a generic
`orbit job resume`.

When a held or review pull request's red checks are inherited from a base-branch
failure that the base has since fixed, an operator can refresh its head onto
the base tip instead of repairing the candidate. See
[refresh a held or review pull request](loop-stalled-prs.md#refresh-a-held-or-review-pull-request).

Under an `--auto-fix` drain, a `review` task held on one of
the codes marked *auto-fix pass* below is handed back to its completion step
by a later drain pass (or the dashboard's **Fix PR**), at most 3 times per pull
request, head and code with a growing wait between passes; once that is
spent the pass lists the task under `auto_fix.skipped` with the hold code as
its reason, and the next step is yours.

| Code | Decision | Next step |
|---|---|---|
| `delivery_head_changed` | The pull request reports a head different from the one this run published. | When the hold message carries an `auto_fix_stopped:` diagnostic, an `--auto-fix` pass (or **Fix PR**) hands the leaf back to completion once the published head, or a head produced by an Orbit-audited clean base refresh of it, reports green required checks (or a forge-confirmed zero-required-check base). Otherwise, if the current head is neither the published head nor an Orbit-audited clean base refresh of it, compare the pull-request head against the published candidate, then start a new delivery attempt on the current head. |
| `delivery_evidence_stale` | Pinned delivery identity is missing or cannot be confirmed, or merge evidence is contradictory. An owner landing of an already-landed or no-diff delivery also holds here, with the stop recorded and the candidate kept in review, when the task's scope (requirements, selectors, relations or comments) changed after the evidence was captured (`already_landed_unverified: task scope changed at scope.<field>`); revalidate against the current task, then hand off again. | *Auto-fix pass:* the next pass hands it back and completion re-reads its pins. When the pass reports it spent, re-establish the pinned identity and confirm the merge evidence, then start a new delivery attempt. |
| `delivery_repair_dispatched` | A repair was already admitted for the blocked head. This includes a duplicate `--auto-fix` admission for that head that observes a repair an earlier run already admitted while that run may still be live, an in-budget check repair whose recovery ran but returned an unsuccessful outcome, or whose decision admits no retry (a clean no-edit result is the exception below), and a no-edit repair whose one unchanged-head rerun is already spent in CI history (no rerun or refresh is sent). A clean no-edit repair is not this hold: its failed checks rerun once on the unchanged head first. A scope or ledger refusal, where the host refuses a repair’s edits, commit or no-edit rerun record before the retry, fails the step with that refusal and is not this hold either. A check repair the job cannot route because it has no `step_failure_recovery` is not this code: that initial hold is `delivery_check_repair_activity_absent`, and no recovery ran. When the no-edit rerun ran and failed again, completion first tries one base refresh of the head; see [A failed no-edit rerun](run-debugging-no-edit-rerun.md#a-failed-no-edit-rerun-refresh-before-hold). A run still `running` after that refresh is pending recovery, not a hold. A `held` run with this code is a confirmed hold; its reason says whether the refresh was refused or was not attempted. | *Pending:* do not push or start a new attempt; a new head would be refused as `delivery_head_changed`. *Confirmed:* when the hold message carries an `auto_fix_stopped:` diagnostic, an `--auto-fix` pass (or **Fix PR**) hands the leaf back to completion once the published head, or a head produced by an Orbit-audited clean base refresh of it, reports green required checks (or a forge-confirmed zero-required-check base). When it carries an unrepaired `pr_auto_fix_check_repair:` hold without `auto_fix_stopped:` or a post-recovery `pr_complete` wrapper, an `--auto-fix` pass (or **Fix PR**) retries through the per-PR ledger while a blocker and budget remain; hands back when required checks are green on the published head or a head produced by an Orbit-audited clean base refresh of it (or the forge confirms zero required status checks on the base); or reports `budget_exhausted` or a policy skip with remaining budget. Otherwise follow the matching case in that section. If a repair is running, let it finish. Once the prior run ends, inspect the hold reason and any recovery attempt. If the no-edit repair’s unchanged-head rerun is spent and checks still fail, repair and publish a new head, then start a new delivery attempt. If check recovery was unsuccessful and the no-edit rerun is not spent, configure `step_failure_recovery` if missing; a new authorized delivery run can use remaining per-PR repair budget on the same head, or you can repair and publish a new head. |
| `delivery_pr_draft` | The pull request is still a draft. | Mark the pull request ready for review, then start a new delivery attempt. |
| `delivery_pr_closed` | The pull request closed without merging. | Reopen the pull request or open a new one, then start a new delivery attempt. |
| `delivery_task_not_promotable` | The task's current status refuses promotion. | Move the task to a promotable status, then start a new delivery attempt. |
| `delivery_landing_conflict` | Landing requires a conflict repair with fresh validation and a new handoff. | Repair the conflict, revalidate, and hand off again. |
| `delivery_requirements_unsatisfied` | Required reviews or checks are unsatisfied, without a failed check. Pending-only owner landings keep waiting within their check-wait budget instead of stopping on this hold; non-auto-fix completion with readable policy stops on this hold even when only a non-required check is still running, and never arms auto-merge on that head. When current policy is unreadable, completion without auto-fix instead re-polls up to four polls, and an unpinned, ungated run may arm auto-merge while that grace reports pending. | Satisfy the named gate. A stopped authorized owner landing with typed `waiting_gate` evidence resumes automatically after a fresh observation confirms the gate cleared, for at most three retries with 60/120/240-second minimum backoffs; explicit retries count toward that ceiling. Use **Retry landing** or `orbit task retry-handoff` for other stops and after the automatic retry budget is exhausted. *Auto-fix pass:* a held delivery leaf is handed back to completion; other deliveries need a new attempt. |
| `delivery_base_checks_pending` | Failed checks are inherited from, or suspected to affect, the base; the base's own result comes before candidate recovery. | Wait for the base's own check result; do not run candidate recovery first. *Auto-fix pass:* the next pass hands it back to completion, which reads the base again. |
| `delivery_completion_budget_expired` | The completion budget expired before completion could be confirmed; the last observed pull-request state was unmerged and the task stays in review. A hold does not cancel auto-merge, and another actor may have merged since, so the forge is authoritative. | *Auto-fix pass:* the next pass hands it back to completion with a fresh budget. Otherwise, or once the pass reports it spent, check the forge for the current pull-request state, then start a new delivery attempt. |
| `delivery_check_evidence_inconclusive` | An auto-fix stop whose check evidence could not be read conclusively; no repair agent runs. | *Auto-fix pass:* the next `--auto-fix` drain pass hands it back to completion, which rereads the pull-request status. Do not dispatch a repair on that evidence. When the pass reports it spent, read the failed jobs yourself. |
| `delivery_forge_observation_unavailable` | Read-only forge reads kept failing with a transport error before any completion mutation (after retries, with no final recovery, past the completion budget, or after repair provenance), or final recovery successfully applied a current-policy requeue or parked the requeue for a human for the unchanged publication. When final recovery requeued, the task returned to `backlog`; when parked, it is `blocked` for a human; otherwise nothing changed on the forge and the task stays in `review`. | When the task is in `review`, run `orbit job resume <run_id>`: it reads the forge again and continues completion from its checkpoints (*Auto-fix pass:* an `--auto-fix` drain pass also hands it back). When the task was requeued to `backlog`, do not resume this held run; let the next delivery attempt run the requeued task (or completion repair readmits it). When the task was parked to `blocked`, inspect and unblock or requeue the task for a human. The task's recorded requeue/park disposition is the authoritative next step. |
| `delivery_origin_unavailable` | The origin could not be reached while admitting backlog tasks; the run is held without changing those tasks. | Wait for the origin to recover; a later normal admission retries the work. A task already in progress follows ordinary run failure handling instead. |
| `delivery_check_repair_activity_absent` | An in-budget auto-fix check repair was admitted, and the job has no `step_failure_recovery` to run it. No repair agent runs, but the admission remains in the per-PR ledger and spends one repair attempt. This is the missing-route hold only: no recovery ran. A recovery that ran and left no admissible retry, a spent no-edit rerun, or a duplicate admission observing an earlier run's repair while that run may still be live holds as `delivery_repair_dispatched`, not this code. That row also says a clean no-edit rerun is not a hold and a scope refusal fails the step. | Because this held run is terminal, configuring `step_failure_recovery` and starting a new authorized delivery run on the same head admits another repair attempt while per-PR budget remains, or repair and publish a new head, then start a new delivery attempt. Exhausting the per-PR budget still fails the run. |
| `delivery_check_runs_absent` | The head this run pushed reported no workflow run at all, and no run of any required check, for five minutes. A workflow run the forge already reports for that head, including one `queued`, `pending`, `waiting`, `requested` or `in_progress`, is checks still pending: completion keeps its normal budget and does not re-request checks or take this hold. With no workflow run, completion re-requests hosted checks once (recorded as `pr_checks_retrigger_requested` in the task history; on GitHub by closing and reopening the pull request, which keeps its head, branch and reviews), and holds if no required check run has started five minutes later. The head is unchanged, no repair is spent and the task stays in review. A later completion attempt on the same head holds again without re-triggering. Pending, queued, failed or skipped required checks never take this path. | *Auto-fix pass:* once the published head, or a head produced by an Orbit-audited clean base refresh of it, reports a required check run or the forge positively confirms zero required status checks on the base branch, the next pass hands the task back to completion. Until then (including when required-check policy is missing or unreadable) the pass lists it under this code and spends no hand-back. If no check run appears, confirm the forge runs workflows for the repository (Actions enabled, workflow triggers, outages), then start the required checks on that head by hand or push a new head. |
| `delivery_landing_repair_requeue` | A required check was classified as caused by the candidate. The claim already ended. The task returned to the backlog with the candidate kept, or it is blocked once the landing repair budget is spent. The landing run is held and is not a failure. | The next run repairs that candidate. Do not resume this held run, and do not hand it back to completion. |
| `review_budget_exhausted` | Review admission found the candidate already reviewed (`review_candidate_reviewed`) or its minutes spent (`review_minutes_exhausted`); the early minutes preflight holds the same way. The run is held, outside failure counts, without retry, recovery or a failure handoff. The ledger, task status and recovery text are preserved; no new review is reserved. | Follow the message's exact recovery command. For a local run, record `orbit task review-reset <task-id> --lineage '<exact-lineage-key>' --reason '<decision>'`, then resume, or start a fresh delivery run. For a claimed leaf, requeue the task on its owner for a fresh claim; do not reset or resume that leaf. |
| `delivery_source_repair_decision` | `candidate_resume` refused a published candidate that an operator must either inspect as explicit source repair or discard. The held reasons are no unique requeue binding, a publication that predates the current binding, a retained local branch that moved, a source that is not an exact owner-local single-task execution, and a source that is live, discarded, changed, or lacks an applied requeue. The run is held, outside failure counts, without retry, recovery or a failure handoff. The refusal message is unchanged. The task status is unchanged: nothing requeues, discards, or resumes. Untrusted preservation, a missing operator reservation, a changed remote or pull-request identity, a missing local identity, and other authority refusals still fail the run. | Follow the message: inspect explicit source repair for the publishing run, or discard the candidate with `orbit task update <task-id> --status backlog --discard-candidate` so the next run implements fresh. Do not resume this held run. |
| `delivery_stale_branch` | `worktree_setup` refused to reuse or move something it does not own, in one of two places. Both hold the run outside failure counts, without retry, recovery or a failure handoff; a claimed leaf settles as `delivery_hold` (`counts_as_failure: false`) and holds the owner task for an operator decision without suppressing the drain's host or crew. *Retained branch:* an existing branch or registered checkout whose tip does not match the freshly resolved base; the message says `refusing stale branch` and names the branch, its tip and the base. Setup leaves it untouched and refuses to reset or discard unexplained history. *Owner base:* a `base_sync: local` run tries a best-effort `origin` fetch when an `origin` remote exists. With no origin or a failed fetch, setup falls back to the local base. After a successful fetch, an owner already equal to or ahead of `origin/<base>` also uses its local commit. If origin is ahead, a clean owner starts from the fetched commit without moving the owner; tracked changes in that behind checkout refuse admission (untracked files do not count). A diverged owner is a separate `delivery_stale_branch` refusal regardless of tracked changes. These owner-base refusals say `refusing stale base` and name the owner checkout, branch and both commits. A diverged base that no checkout holds says so instead and names only the branch and both commits. For local-landing mode, setup separately checks tracked cleanliness in the landing checkout; that readiness refusal can occur even when owner-base freshness passes and uses its own error. Setup has not created a new candidate for this attempt, though a branch or checkout retained from earlier work may still exist and is covered by *Retained branch*. | *Retained branch:* inspect the retained branch or worktree, then move the branch aside or delete it only after confirming no retained work is needed; retrying setup without that recovery will refuse again. *Owner base:* for a tracked-change hold on a behind checkout, preserve its tracked work, then reconcile it with origin. For a divergence hold, preserve owner-only commits by pushing or branching them before reconciling (for example with `git merge --ff-only origin/<base>`, a rebase or a merge). Do not delete the owner checkout. When no checkout holds the diverged branch, reconcile that branch itself with `origin/<base>`, not a checkout. For a separate local-landing readiness refusal, clean tracked changes in the landing checkout and retry. Start a new delivery attempt after resolving the applicable hold. |
| `owner_signoff_required` | The implementer stopped because recorded owner approval is still missing; no agent can record it. The run is held, the task is blocked with the declared message, and the candidate is committed on the run's branch. The handoff tries to carry it to a durable ref and names it in a system comment and `candidate_held` history entry. No PR was opened. If the push fails, the comment says the candidate is host-local; a run on another host cannot fetch it. | Record the approval on the task, move it back to `backlog` (or `in-progress`), and start a new delivery run. A successful push lets that run resume the candidate from any host. If the comment says host-local, recover or push the named head before routing the run to another host. Do not resume this held run. |
