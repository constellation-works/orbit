# orbit-engine

Run a v2 activity or job to completion: template resolution, dispatch to a provider CLI or deterministic action, step results and audit rows, retry/resume/fan-out/concurrency. Owns *how* work runs; catalog placement, authorization, and task lifecycle are Core's. Never depends on `orbit-core`, `orbit-cmd`, or a transport crate.

- `RuntimeHost` (`context/hosts/runtime_host/mod.rs`) is the single capability boundary; Core implements it. A new capability is a new required trait method (no default body) that Core's host implements, plus its answer for a host without it in the test-only `NullRuntimeHost` (`context/hosts/null_host/defaults/host.rs`, behind `test-support`) — never a widened dependency, a threaded runtime handle, or a direct `orbit-store` read. Test doubles implement `test_support::NullRuntimeHost`, never `RuntimeHost` directly.
- The port owns its executor, sandbox, outcome, error and declared-failure evidence key (`DECLARED_FAILURE_EVIDENCE_KEY`) contracts in the leaf `context/dispatch_contract.rs`, which names no `crate::` module. `activity_job::dispatcher` explicitly re-exports the public contract types to preserve existing public paths; migrating consumers and retiring that shim is a follow-up. Sandboxed child spawning lives in the crate-root leaf `sandbox_spawn.rs` (naming only `crate::context`), below both `executor/automation` and `activity_job`; `activity_job::cli_runner::spawn` is a narrow compatibility re-export shim whose retirement is a follow-up, and `spawn_diagnostics.rs` stays in `cli_runner`. The in-crate order is `context::dispatch_contract < sandbox_spawn < executor/automation < activity_job`. The dependency guard (`scripts/check-dependency-direction.sh`) keeps `context` from naming `activity_job` (including test-support code), `sandbox_spawn` from naming any `crate::` module except `context`, `executor/automation` from naming `activity_job` or its crate-root re-exports, and `activity_job` children from reading `DECLARED_FAILURE_EVIDENCE_KEY` from the `activity_job` root.
- `orbit_agent` is used in `activity_job::cli_runner`, `activity_job::audit_writer`, and `activity_job::sqlite_sink`; the crate root also re-exports `provider_supports_continuity`.
- `activity_job::cli_runner::supervisor/` runs provider children on `orbit_common::process::supervisor`, which owns the wait loop, pipe workers and stdin writer. It keeps only the engine's side: the provider request and hooks (`spawn.rs`), the rolling head/tail capture with redaction and protocol tail (`capture.rs`), and the per-line trace events of its output sink (`output.rs`). Its sibling `tests/` files mirror those concerns.
- `activity_job::cli_runner::orchestrator/` splits provider dispatch under `dispatch/` into tool/context preparation, provider envelope/environment/argv and sandbox admission, subprocess supervision, and post-run persistence and completion, with the public entry wrapper in `entry.rs`, child environment helpers in `environment.rs`, and audit/output helpers in `evidence.rs`.
- `activity_job::job_executor::recovery/` groups step recovery retries, decisions, invocation, bounded input, repair commits, evidence and observation. The job-level final recovery hook is under `job_executor/final_recovery/`, split into types, input construction, orchestration, decision admission, and settlement/evidence helpers.
- `executor/automation/vcs/freshness/` separates PR rebasing, interrupted-rebase recovery, divergence and certified checkpoint lookup; `mod.rs` re-exports the existing VCS surface.
- `executor/automation/` holds deterministic step actions; each new operation gets a file, not another arm.
- `executor/automation/vcs/operations/` separates private operation dispatch, input parsing, process execution, push retries, and the PR operation family under `operations/pr/` (queries, create, merge, branch/close mutations, body edits, labels, and ready transitions). `vcs/candidate_resume/` separates candidate lookup from applying and recording a resume; required candidate validation remains in `candidate_validate.rs`. Candidate resume reads the pull-request answer and the source-repair identity predicate from `vcs::pr_answers` and does not name `pr`. The order is `pr_answers < candidate_resume < pr`.
- `executor/automation/vcs/landing/` splits the owner's handoff landing by phase; failed hosted-check classification lives in `vcs/checks/`, shared by landing, PR auto-fix and completion, base refresh and claim; `vcs/pr/complete/` splits PR completion the same way. `vcs/pr/auto_fix/` separates admission and stop verdicts, check classification, repair evidence, published-head adoption, and local publication; `vcs/pr/open/` separates create-or-reuse, templates, superseded PR closure, evidence, and lookup/output projection. `vcs/base/` groups the modules that keep a delivery current with its base, and `vcs/required/` runs a required validation command and keeps its bounded output and evidence.
- `vcs/pr/delivery/` separates delivery identity from check state; `vcs/git/` separates command execution, fetch and timeout budgets.
- The private PR operations' answers (`pr.status`, `pr.view`, `pr.list`, `pr.merge_capabilities`, `pr.merge`, `pr.required_checks`) are parsed once in `vcs/pr_answers/answers.rs`; readers, Core's included, take those types and never index the response by provider field name. The source-repair identity comparison lives in `vcs/pr_answers/identity.rs`, below candidate resume and `pr`. The order is `pr_answers < candidate_resume < pr`.
- `DispatchError`/`CatalogError` translators stay in this crate (`scripts/check-error-translation.sh`).
- No local `fn redact_*` in `cli_runner` (`scripts/check-artifact-redaction-guardrail.sh`); child environments are composed via `orbit_common::security::child_env` over a cleared env, never inherited.
- Step results are durable: any `job_executor` accounting change needs resume/recovery test coverage, not just the happy path.
- The crate-root `tests/engine/` binary holds end-to-end runtime/CLI-agent/local-shell/name-resolution/worktree-lifecycle/PR-landing/history-note integration modules; `examples/` holds runnable smoke programs. `pr_landing.rs` leaves `run_private_vcs_operation` at its `NullRuntimeHost` default, so the real provider adapter runs against a substitute `gh` backed by a bare Git remote.
