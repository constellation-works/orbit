# orbit-engine

Run a v2 activity or job to completion: template resolution, dispatch to a provider CLI or deterministic action, step results and audit rows, retry/resume/fan-out/concurrency. Owns *how* work runs; catalog placement, authorization, and task lifecycle are Core's. Never depends on `orbit-core`, `orbit-cmd`, or a transport crate.

## Rules

- Core implements the capability traits in `context/hosts/runtime_host/`. `RuntimeHost` declares no method and has a blanket implementation over `RunLifecycle`, `ReviewGate`, `HostEnvironment`, `Dispatch`, `Recovery` and `RuntimeHostProcessEnvironment`. Bound functions by the capabilities their code and callees use. Add capabilities as required methods on the owning trait and supply defaults for `NullRuntimeHost` (`context/hosts/null_host/defaults/host.rs`, behind `test-support`). Keep runtime handles and capability-owned store access behind that boundary. Test doubles for narrow entry points implement the needed traits. Full-runtime fixtures use `test_support::NullRuntimeHost`.
- The port owns its executor, sandbox, outcome, error and declared-failure evidence key (`DECLARED_FAILURE_EVIDENCE_KEY`) contracts in the leaf `context/dispatch_contract.rs`, which names no `crate::` module. `activity_job::dispatcher` explicitly re-exports the public contract types to preserve existing public paths; migrating consumers and retiring that shim is a follow-up. Sandboxed child spawning lives in the crate-root leaf `sandbox_spawn.rs` (naming only `crate::context`), below both `executor/automation` and `activity_job`; `activity_job::cli_runner::spawn` is a narrow compatibility re-export shim whose retirement is a follow-up, and `spawn_diagnostics.rs` stays in `cli_runner`. The in-crate order is `context::dispatch_contract < sandbox_spawn < executor/automation < activity_job`. The dependency guard (`scripts/check-dependency-direction.sh`) keeps `context` from naming `activity_job` (including test-support code), `sandbox_spawn` from naming any `crate::` module except `context`, `executor/automation` from naming `activity_job` or its crate-root re-exports, and `activity_job` children from reading `DECLARED_FAILURE_EVIDENCE_KEY` from the `activity_job` root.
- Module layout: [architecture page, Module layout](../../docs/architecture/orbit-engine.md#module-layout).
- `executor/automation/` holds deterministic step actions; each new operation gets a file, not another arm.
- Candidate resume reads the pull-request answer and the source-repair identity predicate from `vcs::pr_answers` and does not name `pr`. The order is `pr_answers < candidate_resume < pr`.
- The private PR operations' answers (`pr.status`, `pr.view`, `pr.list`, `pr.merge_capabilities`, `pr.merge`, `pr.required_checks`) are parsed once in `vcs/pr_answers/answers.rs`; readers, Core's included, take those types and never index the response by provider field name. The source-repair identity comparison lives in `vcs/pr_answers/identity.rs`, below candidate resume and `pr`. The order is `pr_answers < candidate_resume < pr`.
- `DispatchError`/`CatalogError` translators stay in this crate (`scripts/check-error-translation.sh`).
- No local `fn redact_*` in `cli_runner` (`scripts/check-artifact-redaction-guardrail.sh`); child environments are composed via `orbit_common::security::child_env` over a cleared env, never inherited.
- Step results are durable: any `job_executor` accounting change needs resume/recovery test coverage, not just the happy path.
- The crate-root `tests/engine/` binary holds end-to-end runtime/CLI-agent/local-shell/name-resolution/worktree-lifecycle/PR-landing/history-note integration modules; `examples/` holds runnable smoke programs. `pr_landing.rs` leaves `run_private_vcs_operation` at its `NullRuntimeHost` default, so the real provider adapter runs against a substitute `gh` backed by a bare Git remote.
