Show what each kind of delivery costs on this host, minute by minute

Usage: orbit run profiles [OPTIONS]

Options:
      --accuracy
          Compare recorded admission forecasts with the host's measured load

      --root <ROOT>
          Override the Orbit root directory (highest precedence)

      --since <TIMESTAMP>
          Include forecasts at or after this RFC3339 timestamp (accuracy only)

      --workspace <SELECTOR>
          Select a workspace by registered name, logical ID (`ws_*`), or absolute checkout path. Distinct from `--root`, which overrides the Orbit data directory. Only active workspaces may be bound; commands fail if the workspace status is not active

      --drain <RUN>
          Select an exact drain run id (accuracy only)

      --mode <MODE>
          Select the recorded admission mode: shadow or enforce (accuracy only)

      --format <MODE>
          Output format (default: auto — a table on a terminal, plain text when piped)

          Possible values:
          - auto:   Decide from the sink: a table on a terminal, plain text otherwise
          - table:  Aligned columns with a header
          - plain:  Untruncated text with tab-separated fields and no header
          - json:   A single JSON document
          - ndjson: One complete JSON document per line

      --json
          Output as JSON (shorthand for --format json; always pretty-printed)

  -h, --help
          Print help (see a summary with '-h')

Lists one resource profile per workspace, work class and complexity, learned from the CPU and memory each delivery's workers recorded. A delivery is the chain of runs for one task, counted from its admission; resumed or retried deliveries are left out. Each profile covers the key's last `machine.auto_concurrency.profile_window` completed deliveries from the last 30 days. `auto-task:<template>` profiles have no complexity.

HORIZON is the minute at which fewer than one in ten deliveries is still running, capped at `horizon_cap_minutes`. PEAK_CPU is the highest mean cores before it and PEAK_MEM the highest 90th-percentile memory, each with the minute it occurs. SPREAD says how far deliveries disagree with that average (per-minute standard deviation over mean, for CPU and memory): near 0 is a profile stable enough to forecast with, near or above 1 one that is not. DELIVERIES marks a key with fewer than `min_profile_deliveries` as sparse; a lookup for it falls back to a wider profile.

BUILD_FLAG marks no-diff profiles, and templates whose tasks are `no-diff-expected`, where a delivery used more than 1 core for 2 minutes in a row: work that should make no diff is building. The deliveries behind each flag are named below the table. Templates that build by design, such as qa-sweep, are never flagged.

`--json` emits every profile with its full per-minute series (alive, cpu_cores, cpu_stddev, memory_bytes, memory_stddev_bytes), its deliveries and its flagged deliveries.

`--accuracy` reports instead how well the host load forecast held up, from what drains in effective auto-concurrency mode `shadow` or `enforce` recorded each admission pass over the last 30 days by default: the forecast 5, 10, 20 and 30 minutes ahead, counting what the pass admitted, against the host's measured CPU and memory for that minute. Error is forecast minus measured: MEAN_ERR is its mean, UNDER how often the forecast was below the measured load, and WORST the largest miss with the minute it forecast. PENDING counts target minutes that have not fully ended at report time, even if partly measured; MISSING counts ended minutes without measurements. Their sum is the compatible unmeasured count. Only ended measured minutes form error pairs. Below, per drain, its shadow passes against what it admitted: WOULD_HOLD counts the tasks it admitted that gap fit would have held, WOULD_ADD those gap fit would have admitted that it did not. Pull drains record one forecast per request, counting a returned claim. PULL_REQUESTS counts these forecasts, PULL_SENT the requests sent to the owner, and PULL_WOULD_HOLD the shadow requests enforce would have held because no work fit. `--json` adds every forecast point paired with its measured minute.

Accuracy selectors compose: `--since` is an inclusive RFC3339 forecast timestamp (default: 30 days ago), `--drain` matches an exact drain run id, and `--mode shadow|enforce` matches the recorded mode. Forecast timestamps are bounded by one report-time snapshot. Text and JSON echo the effective selection. This read-only report does not attest source revision, build budget or thresholds: a drain/time cohort is an operator selection, not proof of homogeneous configuration. Per-task profiles are a separate population; sparse deliveries or wide spread do not become calibrated confidence from selecting an accuracy cohort.

Examples:
  orbit run profiles
  orbit run profiles --json
  orbit run profiles --accuracy
  orbit run profiles --accuracy --json
  orbit run profiles --accuracy --since 2026-10-15T00:00:00Z --drain <RUN> --mode enforce --json
